# libuvcpp 每连接内存与吞吐实测

这一页是一次**可复现的靶场实测记录**，被测对象是**用本库构建出来的一个真实 HTTP 服务**，
不是微基准，也不是估算值。写它的直接动机是回答一个具体问题：

> 一台机器上一百万条空闲长连接，要吃掉多少内存？

| 项 | 值 |
|---|---|
| **测量版本** | **1.1.33**（`534e4ed`） |
| 撰写时 `master` | `1.1.35-dev`（`d46b6eb`） |
| 口径收口于 | tag `v1.2.0`（为什么收口在这里、以及 1.2.0 为什么不在测量路径上，见 §1） |
| 被测服务 | 靶场：静态文件 + 动态路由 + 上传下载 + WebSocket + TLS 的完整 webapp |
| 平台 | Windows 10 Pro 1903（18363）/ MSVC x64 / Release |
| 运行时 | 单事件循环线程（下文另注明） |

**三个读数**（方法、分档与原始数据见下文各节）：

- **每连接内存 4.62 KiB**（4 734 B，最小二乘，**R² = 0.999987**）⇒ 外推 100 万连接 ≈ **4.42 GiB**
- 单核动态路由 **75 k RPS**（流水线 10–50 深可到 **88 k**）；静态 **44 k RPS / 107 MB/s**
- 10 分钟长跑 **3 840 万请求、0 错误**，RSS 漂移 **0.2%**

上面那三个读数是**本机靶场**（§4.1–4.4）。**平台那一套装置**（HttpArena，64 核参考机、
平台自己的生成器）的读数在 **§4.5**，其中 **1.7.0 那一轮**相对上一轮发布版 `v1.6.1`
的提升一览就是那一节的第一张表 —— 一句话版本是：h3 那一格 **×20 121**（58 → 1 167 034
req/s）、ws 流水线 **×2.3 ~ ×2.8**、`baseline-4096` **+44%**、`pipelined-4096` **+88%**、
`json-*` **+67% ~ +81%**、`static-h2` 的**常驻内存 3.7 GiB → 793 MiB**（吞吐同时 +54%），
而 42 档的 `5xx` 全为 0。

## 1. 为什么这是「1.1.33 的读数」，以及它为什么对后面几版仍然成立

测量发生在 `534e4ed`（1.1.33）。写明这件事是**必要条件**：一个不带 commit 的读数值
不是结论，是传闻。

`534e4ed` 之后到本文撰写时的 `d46b6eb`（1.1.35-dev）之间，**`src/` 下只动了三个文件**：

```
src/uvcpp/uvcpp_version.h      |  2 +-          ← 版本号
src/web/uvcpp_http_server.cpp  | 31 +++++-----  ← 压缩变体表的字节账
src/web/uvcpp_http_server.h    | 10 ++++++-
```

其余全是文档、CI、测试与发布打包。逐个说清它们为什么不在本文的测量路径上：

| commit | 动的东西 | 在本文测量的路径上吗 |
|---|---|---|
| `4710479` | 版本号 1.1.33 → 1.1.34 | 不涉及 |
| `d56c2a4` | 压缩变体表的字节账：把会漂移的计数字段换成从容器派生的求和，并补上「字节上限」那条腿 | **不在** —— 见下 |
| `d46b6eb` | 发布包同时提供 Debug 档动态库与 PDB（`uvcppd.dll` / `libuvcppd.so`），只改打包器与 CI 判据 | 不涉及 Release 运行时 |

`d56c2a4` 只影响「变体表超过上限时淘汰谁」，且只在**压缩缓存的冷路径**上；本文测的是连接
内存、动态/静态吞吐、长跑稳定性，都不经过那条路径（本文这一版连压缩都没开）。

**因此：下面的读数对 1.1.33 – 1.1.35-dev 这条线成立**；版本号只升不改功能时（1.2.0 属此
列）同样成立。真去动了上面那三条路径的话，这一页需要重测 —— 复现方法在第 8 节。

上面两段是**撰写时的快照**（`d46b6eb`）；收口在**发布提交**上：`534e4ed..v1.2.0`
（`d67f1f4`）在 `src/` 下仍然只有同样三个文件 —— `uvcpp_version.h`、`uvcpp_http_server.cpp`、
`uvcpp_http_server.h`。`uvcpp_version.h` 在那张表里是 `2` 行、到这里是 `8` 行，差的是发版
时把 `UVCPP_VERSION_IS_RELEASE` 置 `1` 与版本号 1.1.35 → 1.2.0，**不是新代码**；另两个文件
的改动量逐字相同。所以 **1.2.0 这一版照样不在本文的测量路径上**，下面的读数对发布版成立。

（锚点用 tag `v1.2.0` 而不是「最新一次发布」：tag 不会动，而后者会随下一个版本改变所指。）

## 2. 方法：为什么是外推，而不是真的造满一百万

**真造不满。**本机在 **54 852** 条时开始出现 `ENOBUFS` —— 那是动态端口与内核缓冲到顶，
不是服务端拒绝。换平台也一样有这条墙，只是位置不同（对照项目在自己的 Linux 环境里撞到的
是同一量级的另一个数）。所以百万级只能外推，而外推要立得住，就必须有判据。

做法是**多档位建立连接 + 最小二乘回归 + R²**：每档记「建立 N 条连接后的进程 RSS」，对 N
做一次线性拟合，斜率就是每连接内存，再外推到 1e6。判据不是"斜率好看"，是**R² 必须接近
1**，且每档残差要小 —— 否则那条直线根本不存在，外推就是编。

- 采样对象是**进程 RSS**（`WorkingSet64`），即**用户态**每连接开销；内核侧的 TCP 缓冲
  （每连接约 4 KB 量级）不在其中，也不受本库控制 —— 第 6 节比较时会回到这一点。
- 每档建立连接后**逐条复检**该连接可服务（不是"连上就算"）。
- 关闭后复检句柄数回落，确认没有把连接泄漏成别的形状。

## 3. 结果一：每连接内存

下表有**两列 RSS，是两个不同的量**，别混：

- **建立后 RSS** —— 连接全部建好、攥住时读的。**拟合用的就是这一列。**
- **关闭后 RSS** —— 全部断开之后再读的。它是**另一条线**，只用来佐证连接被回收干净
  （本节末单说）。

八档采样（原点 + 7 个非零档）：

| 目标并发 | 实际建立 | 连接失败 | 探测成功 | **建立后 RSS**（拟合用） | 关闭后 RSS / 句柄 |
|---:|---:|---:|---:|---:|---|
| 0（基线） | — | — | — | **9.402 MiB** | — |
| 8 000 | 8 000 | 0 | 8 000 | 46.277 MiB | 17.398 MiB / 184 |
| 16 000 | 16 000 | 0 | 16 000 | 82.602 MiB | 24.320 MiB / 184 |
| 24 000 | 24 000 | 0 | 24 000 | 118.477 MiB | 31.324 MiB / 184 |
| 32 000 | 32 000 | 0 | 32 000 | 154.238 MiB | 38.531 MiB / 184 |
| 40 000 | 40 000 | 0 | 40 000 | 190.652 MiB | 45.133 MiB / 184 |
| 48 000 | 48 000 | 0 | 48 000 | 226.727 MiB | 52.715 MiB / 184 |
| 55 000 | **54 852** | 148（`ENOBUFS`） | 全部 54 852 | 257.270 MiB | 59.094 MiB / **184** |

- **零连接失败**直到 48 000。
- 每一档都逐条复检过 8 000 – 54 852 条连接**全部可服务**。
- 全部关闭后句柄回落到 **184**（与基线一致，无泄漏）。
- 原点那档是**进程空转时的基线**（9 859 072 B），即 8 个点里的第 8 个。

**拟合（8 个点，y 单位 MiB）**：

```
RSS(MiB) = 0.0045143 × N + 9.954        R² = 0.9999869
         = 4.62 KiB/连接 × N + 9.95 MiB
```

逐点残差（**这一列要能让人自己算**）：

| N | 建立后 RSS (MiB) | 拟合预测 (MiB) | 残差 | 残差 % |
|---:|---:|---:|---:|---:|
| 0 | 9.402 | 9.954 | −0.551 | −5.86% |
| 8 000 | 46.277 | 46.068 | +0.210 | +0.45% |
| 16 000 | 82.602 | 82.182 | +0.420 | **+0.51%** |
| 24 000 | 118.477 | 118.296 | +0.180 | +0.15% |
| 32 000 | 154.238 | 154.410 | −0.172 | −0.11% |
| 40 000 | 190.652 | 190.525 | +0.128 | +0.07% |
| 48 000 | 226.727 | 226.639 | +0.088 | +0.04% |
| 54 852 | 257.270 | 257.571 | −0.301 | −0.12% |

- **除原点外每点 |残差| ≤ 0.51%**；而上表能看出这些残差**没有走向**（在零点附近交替），
  不是单向偏。
- 原点那点自己偏 −5.86%：它是**空转基线**这一次单独的读数，不落在拟合线上 —— 拟合出的
  截距 9.954 MiB 比它高 0.55 MiB。写出来是因为"除原点外"这句话要是没有上面那张表，读者
  没法知道偏多少。
- 截距 9.95 MiB 是进程的固定开销（静态缓存、会话表、已初始化的协议层等），不是每连接的。
- **外推 100 万连接 ≈ 4.4085 GiB（斜率）+ 0.0097 GiB（截距）≈ 4.42 GiB。**
- 每连接 **4 733.6 B = 4.6226 KiB**，本文按 4.62 KiB 记。

**为什么能这么低**：本库**没有每连接常驻的读缓冲**。读是
`read_start([](uvcpp_buf* b){ … })` 的按需形状 —— 有数据才给缓冲，空闲连接上不预置任何
一块固定大小的读缓冲。这一条是第 6 节那个对照的全部原因。

### 「关闭后」那一列是另一条线，不能拿去验上面的拟合式

上表最右列（关闭后 RSS）**自己对 N 回归**，出来的是：

```
RSS(MiB) = 0.0008870 × N + 10.120     R² = 0.9997352
         = 930 B/连接
```

斜率是 **5.09×** 的差（4 733.6 ÷ 930.1），R² 也不是上面那个 0.9999869。**这两个数都对，
但它们量的不是同一件事**：关闭后读到的是一条正在被回收的服务端连接表的残余占用，不是
「多一条连接要多多少内存」。**要判定容量，看的是「建立后」那条线。**

这一列自己的价值在另一头：它的**截距 10.120 MiB 与空转基线 9.402 MiB 只差 0.72 MiB**
（约 7.7%）。这才是"连接被回收干净"的证据 —— 8 000 到 54 852 条连接全关掉之后，进程回到
离基线不远的地方，且**句柄一律回到 184**。所以这一列留着，但它是**证据**，不是**斜率**。

## 4. 结果二：吞吐与延迟

动态路由（内存型响应），单事件循环：

| 用例 | 并发 | 流水线 | RPS | p50 | p99 | max | 错误/超时/503 |
|---|---:|---:|---:|---:|---:|---:|---:|
| json | 1 | 1 | 44 946 | 0 ms | 0 ms | 1 ms | 0 |
| json | 10 | 1 | **75 791** | 0 ms | 0 ms | 1 ms | 0 |
| json | 400 | 1 | 71 614 | 5 ms | 6 ms | 27 ms | 0 |
| json | 1 600 | 1 | 63 278 | 25 ms | 28 ms | 101 ms | 0 |
| json | 100 | **10** | **88 134** | 10 ms | 16 ms | 28 ms | 0 |
| json | 100 | **50** | 87 874 | 56 ms | 65 ms | 94 ms | 0 |

静态文件（走工作线程池）：`44 379 RPS / 107 MB/s`（并发 100）、`43 154 RPS / 104 MB/s`
（并发 400）。256 KB 大响应：`1 608 RPS / 402 MB/s`。

**要点**：到并发 1 600 仍零错误、零超时、零 503，延迟线性劣化但不掉请求；流水线
（10–50 深）把单核推到 88 k RPS。

**静态服务没有并发悬崖**：1 → 200 并发共 12 档打静态文件，**每一档 503 占比都是 0%**，
成功 RPS 从 15 879 升到峰值 **45 044**（并发 12）后平在 43 563（并发 200）。作为对照，
同一台机器上纯内存路由是 44 501 → 73 480。

### 4.1 PR #24 的两处热路径改动（**作者自测，另一套装置**）

> **这一小节的读数不在上面那套装置上。** 它是 PR #24 作者用自己的靶场做的 A/B
> （100 并发 × 15 s × 4 轮，两档**交替**跑）。**绝对值与本节表格不可比** ——
> 有意义的是同一台机器上的**差值**。按既定口径，性能读数**暂用作者发来的**，
> 后续复测再更新这一节。

两处都是"纯白付"：

1. **读缓冲不再清零 —— 每请求 128 KiB。** `uvcpp_buf::alloc_buf()`
   （`src/uvcpp/uvcpp_buf.cpp:474-474`）原先走 `uvcpp_alloc_arry<char>()`，而
   `uvcpp_alloc_*` 全是 **calloc 语义**（分配后整块 `memset` 0，
   `src/uvcpp/uvcpp_alloc.h:45,109`）。这块内存是交给 libuv 的 alloc 回调**接数据**
   的，紧接着就被 `WSARecv` 整块覆盖 —— 清的字节一个都留不下。代价是**量出来的**：
   libuv 对 TCP 流给的 `suggested_size` 是 **64 KiB**，而一条连接在**一次请求**里会让
   alloc 回调跑**两趟** ⇒ 每个请求 **128 KiB**，而请求本身只有百来字节。现在改走
   `uvcpp_buf.cpp` 匿名命名空间里的 `alloc_raw()`（`src/uvcpp/uvcpp_buf.cpp:462-462`，
   契约是"读之前不能假设它是 0"）
   —— **不给它公开的位置**：`uvcpp_alloc_*` 那一族的约定就是"全部清零"，同前缀、
   同形状、唯独不清零的兄弟放进去是个陷阱。它不是公开 API，这是有意的。
2. **响应序列化不再走 `ostringstream`**：`uvcpp_http_response::to_string()` 改成
   `std::string` 直接拼 + `reserve(est)`，状态码与 content-length 两个整数用十行的
   `append_dec` / `append_hex`（绕开 num_put 的 locale、sentry 与虚调用）。

| | QPS | 用户态 µs | 合计 µs | 合计 µs 轮间散布 |
|---|---:|---:|---:|---:|
| 基线 | 101 251 | 4.8500 | 9.8765 | 0.1431 |
| 改动后 | **115 085** | **3.9469** | **8.6896** | 0.1797 |

合计 **−13.66%**、用户态 **−22.88%**、QPS **+12.02%**；第二轮独立复量得 **−15.29% /
−27.84% / +13.17%**。两处差值都在轮间散布之外，全部轮次 0 非 2xx；9 个端点的原始报文
逐字节一致（1 312 B）。拆开单独开关：读缓冲约 **−9.8%**、序列化约 **−2.5%**。

**为什么是"两档交替"而不是跑两遍**：本机 µs 会漂 —— 同一份代码跨会话能从 102 943 漂到
113 802（**+10.5%**），而**同一轮内**散布只有 0.12 µs。所以判据取「|差| > 双方轮间
散布」，而不是两次独立读数的绝对值。

**试过但没采纳**：把读缓冲封顶到 8 KiB（−0.49%，落在散布内，白搭）。而且**不能封在
`alloc_buf()` 里** —— 它同时给 UDP 用（`src/net/uvcpp_udp_server.cpp:165`、
`src/net/uvcpp_udp_client.cpp:828`），而 UDP 是数据报，缓冲小了会**截断报文**。

### 4.2 接受连接时默认关 Nagle（**另一套装置**，轮流 A/B）

> 同 4.1 的口径：这一节的读数不在上面那套装置上，而是 **HttpArena 的条目在这台机器上
> 裸机跑**（同一个 `h2load`、同一份条目二进制，两臂**交替**，各三轮）。绝对值与本节表格
> 不可比 —— 有意义的是**同一轮内两臂的差**与**同一条连接上的对照**。

**缺陷**：libuv 建出来的 socket **不设** `TCP_NODELAY`，于是 Nagle 是开的。一次应答只要
被写成**两段**、每段都小于 MSS，第二段就被压在发送缓冲里等对端的 ACK；而对端此刻没有
数据要回，走的是 Linux 的 **40 ms 延迟 ACK** ⇒ 这一笔应答平白多出 40 ms。h2 上的 gRPC
应答正是两段（头块+DATA 一段、尾随头一段）。

**判据不是"变快了"，是"那个 40 ms 定时器没了"。** 同一台服务器、同一个 `h2load`、同一条
回环上，h1 路由（整条报文一次 `uv_write`，一段）的 `request` 中位数只有 **21 µs** —— 这个
对照组把"回环的固有成本"钉在几十 µs 那一档；而 h2c 上同一条 gRPC 路由是 **41.00 ms**。
三者一比，那 40 ms 只能来自应答的第二段在等人。

| 形状（`h2load`，`-D 5s`，gRPC 请求体是 9 字节帧） | base（改动前） | fix（改动后） |
|---|---:|---:|
| h2c gRPC `-c 1 -m 1` | **24.20 rps**；五秒 **121** 个；`request` 中位 **41.00 ms** | **25 687 / 26 569 / 29 489 rps**；五秒 12.8–14.7 万个；中位 **29 µs** |
| h2c gRPC `-c 64 -m 1` | 1 541 / 1 553 / 1 554 rps；中位 **41.01 ms** | **175 498 / 182 635 / 242 849 rps**；中位 149–229 µs |
| h2c gRPC `-c 256 -m 100` | 594 000 / 595 500 / 529 901 rps | 646 040 / 477 952 / 654 301 rps |
| h2 gRPC over TLS `-c 256 -m 100` | 587 550 / 587 172 / 409 423 rps | 619 631 / 496 094 / 523 543 rps |
| **h1 对照** `-c 1 -m 1` | 39 106 / 41 975 / 42 322 rps；中位 21 µs | 41 587 / 38 618 / 43 134 rps；中位 22 µs |
| **h1 对照** `-c 256 -m 100` | 1 222 788 / 1 555 136 / 1 566 292 rps | 1 583 476 / 1 228 199 / 1 611 052 rps |
| `curl`（客户端自带 `TCP_NODELAY`）单连接打 h2c gRPC，`≥30 ms` 的占比 | 9/30、10/30、15/30 | **0/30、0/30、0/30** |

36 格全部 `0 failed / 0 errored / 0 非 2xx`。三条读得出来的结论：

1. **只在"一条连接上一个请求在途"时咬人**：`-m 1` 两档约 **1 100×** 与 **120×**。
2. **`-m 100` 的持续流水上量不出差别** —— 两臂落在彼此轮间散布里（同一臂三轮自己就能差
   ±15%）。ACK 一直在流，Nagle 最多压住一个 RTT，回环上那是几十 µs、不是 40 ms。
   **所以别把这条当成吞吐优化的战果**：HttpArena 的档位都是 `-m 32` / `-m 100`，它不解释
   榜单上的任何一格。它修的是低并发请求/应答的时延 —— `curl` 那一行是同一件事的另一个
   侧面：客户端自己带 `TCP_NODELAY` 也救不了服务端的第二段。
3. **h1 的两条对照一格没动。** 这是"归因落在两段式应答"而不是"`TCP_NODELAY` 让什么都
   快了"的证据；少了它，第 1 条那两位数的倍率也能被解释成别的东西。

**这套量具的一个坑（记在这里免得下次再踩）**：A/B 是"同一个条目二进制、只换
`LD_LIBRARY_PATH` 下的 `libuvcpp.so`"，所以**必须验证"8080 的持有者就是这次起的那个进程、
它 `/proc/<pid>/maps` 里加载的就是本变体那份 `.so`"**。第一版的启动脚本写成
`( cd X && setsid env … & echo $! > pid )`：`&` 作用在整个 AND 列表上，bash 会为它再 fork
一层子 shell，`$!` 记到的是那层子 shell 而不是 server ⇒ pid 文件从第一轮起就是死的，泄漏
的 server 一直占着 8080，之后每个新 server 都**绑不上就静默退出**，30 格读数其实全来自
同一个进程 —— 两臂的数字因此一模一样，差点被当成"这个修复没用"。修法就是那两条断言：
起完核端口持有者，再核 `/proc/<pid>/maps`。

### 4.3 每请求的用户态指令数（**另一套装置**，callgrind）

> 同 4.1 / 4.2 的口径：这一节的读数**不在**上面那套装置上，也不是 rps。它是
> `valgrind --tool=callgrind` 数出来的**每请求指令数** —— 同一个条目二进制、同一条
> `gcannon` 命令行、同一档核绑定，**只换 `LD_LIBRARY_PATH` 指向的那份 `libuvcpp.so`**。
> **绝对值与本节表格不可比**，跟 4.1 / 4.2 的 µs 也不可比；有意义的是**同一个会话内的差**。
> 装置搭法、六个格式与流程上的坑、以及 `/proc/<pid>/io` 那两次被**证伪**的假设，记在
> [`benchmark-rig.md`](benchmark-rig.md) 的「每请求指令数的量具（callgrind）」一节。

**为什么这次不信 rps 而信指令数**：这台机器的 CPU 跑在 `powersave` 调频档上，同一个
二进制跨会话的 µs/请求能漂 **35%**；callgrind 数的是指令，**与频率无关** —— 同一份 `.so`
四轮下来得 `11 283.3 / 11 284.9 / 11 287.7 / 11 291.8`，**散布 0.075%**。判据因此取
「|差| > 双方自身散布」，跟 4.1 那条是同一个道理。

本轮改了三处（`1.6.17-dev`，逐处说明见 CHANGELOG 的「性能」组）：
`web_parse_query` 按 `&` 的个数预留、`to_string_into` 的响应头表四趟并成一趟、
状态行不再为字面量造 `std::string`。

| 读数（h1 `/baseline2?a=1&b=1`，`-c 2000`、5 s 窗口、callgrind 增量段） | 每请求指令数 |
|---|---:|
| 改动前（四轮） | 11 283.3 / 11 284.9 / 11 287.7 / 11 291.8 |
| 只换序列化（`to_string_into` + `size_to_string`） | 11 205.1 / 11 211.7 |
| 再并上头表遍历、加上查询预留 | **10 925.1 / 10 927.5** |

同一会话内夹逼 **11 286.3 → 10 927.5 = −358.8 条/请求（−3.18%）**；把四轮改动前与两轮
改动后**全部交叉配对**，区间是 **−355.8 ~ −366.7（−3.15% ~ −3.25%）**。

逐函数归因（`so-after3 → so-after4` 这一段，同一会话，合计 **−286.6**）：

| 函数（每请求） | 前 | 后 | 差 |
|---|---:|---:|---:|
| `vector<pair<string,string>>::_M_realloc_insert` | 154.9 | **0** | −154.9 |
| `malloc` / `_int_free` / `free` / `operator new` / `operator delete` | — | — | **−135.7** |
| `__strlen_avx2` | 239.6 | 225.4 | −14.2 |
| `uvcpp_http_response::has_header(const char*)` | 60.4 | 50.3 | −10.1 |
| `web_parse_query`（新增的数 `&` 循环） | 29.2 | **75.4** | **+46.2** |

`_M_realloc_insert` 归零加上分配器那一簇是**查询预留**（净 **−242.4**），`has_header`
连同 `__strlen_avx2` 是**头表合一**（约 **−44**）。序列化那一半落在
`to_string_into` **100.5 → 57.3**、`size_to_string` **76.4 → 65.4** 上，单独量是
**−78.5**（11 286.9 → 11 208.4，与上面那两轮 11 205.1 / 11 211.7 的区间不重叠）。

**改动后的画像**（每请求，前几名）：`__memcpy_avx_unaligned_erms` 862.2（7.89%）、
`string::_M_append` 665.7（6.09%）、`malloc` 523.2（4.79%）、`_int_free` 487.6（4.46%）
—— 分配器那两名合计 **11.0%**，是下一刀的方向；`uvcpp_buf::free_own` 232.7（2.13%）、
`vector<http_header>::emplace_back` 187.9（1.72%）紧随其后。

**试过并整体退回**：把 `web_url_decode` / `web_collapse_slashes` 改写成原地版本
（外加 `take_from` 少一次拷贝）这一整包，在同一量具上是 **+328.6 条/请求** ——
`web_url_decode` 每请求被调 **5.03** 次，其中 4 次是 1 字节的查询键/值，原地版省下的
那次拷贝抵不过多出来的一趟扫描。三处留下来的改动都只动**自己这一趟**、不改任何分支
结果，报文逐字节不变（`to_string()` 与 `to_string_into()` 仍是同一份实现，
`tests/functional/web_app_response_func.cpp` 那条逐字节比对继续覆盖）。

### 4.4 静态文件发盘上孪生（**第三套装置**，探针 + `h2load -p http/1.1`）

> 又是另一套装置：这一节的读数**不在** 4.1 / 4.2 的条目上，也不是 4.3 的指令数。它是一支
> 仓外探针（`probe.cpp`）**一次只起一条静态腿**、`h2load -p http/1.1` 打同一份
> `data/static`（20 个文件 + 30 个孪生）。**绝对值与前几节都不可比**；有意义的是**同一
> 会话内同一台机器上的开/关两臂之差**。装置搭法、三个坑（**语料的文件系统**、`-m` 的
> 含义、`-c 256` 的双峰），记在 [`benchmark-rig.md`](benchmark-rig.md) 的
> 「预压缩孪生：两条静态腿各自的探针」一节。

**要回答的问题**：静态响应在服务端是**每请求现场 deflate 一整份文件**（响应变体缓存按
`resp.cache_tag` 做键，而 `uvcpp_static_server` 到 `1.6.44-dev` 为止都不填它 ⇒ 那个缓存对
它形同虚设，见下），那么"盘上放一份早就压好的孪生、直接发它"值多少？两条静态腿是两份不同
的实现，得分别量。

**这一节在 `1.6.44-dev` 上重跑过（2026-10-14），因为那两条腿的起点变了**：
`uvcpp_static_server` 从 `1.6.44-dev` 起也填 `resp.cache_tag`（从前全仓只有
`uvcpp_web_static` 填），"关"那一臂于是不再是"每请求重压一遍"。下表每一臂都是**同一次
会话内交替跑 3 次取中位数**：

| 腿（ext4 语料、8 循环、`-c 64 -m 2 -n 8000`） | 发盘上孪生**关** | **开** | 差 | 8000 请求送出字节 |
|---|---:|---:|---:|---:|
| `uvcpp_static_server`（`static-h3` 那条腿） | 66 554.63 rps | **89 791.80** rps | **+34.9%** | 173 843 446 → 131 194 904（−24.5%） |
| `uvcpp_web_app::serve_static`（`static-h2` / `static-tls`） | 68 464.43 rps | **92 262.63** rps | **+34.8%** | 173 843 446 → 131 194 904（−24.5%） |
| `uvcpp_static_server`，**把 `cache_tag` 也关掉**（`1.6.44-dev` 之前的形状） | 977.00 rps | — | — | 173 843 446 |

（三次原始读数：`srv` 的 pc=0 为 67 303.24 / 66 554.63 / 64 449.08、pc=1 为
89 791.80 / 90 780.14 / 84 193.69；`app` 的 pc=0 为 62 364.55 / 68 464.43 / 71 858.44、
pc=1 为 92 262.63 / 92 065.14 / 92 707.40；第三行 941.33 / 979.10 / 977.00。）

三条读得出来的结论：

1. **那 88× 曾经是真的，现在不是了 —— 但它从来不是这个选项的功劳**。第三行是**消融臂**：
   同一份源码，只把 `fill_cached_response()` 里填 tag 的那一段关掉、单独链一份
   `libuvcpp.so`，其余一个字节不改。它复刻出旧版的 933.15 rps（今天 977.00）那个量级 ——
   每请求在**循环线程**上把整份文件 deflate 一遍（`compress_enabled_` 默认就是 true，
   而变体缓存按 `cache_tag` 做键，本类从前不填 ⇒ 缓存对它不生效；20 个文件平均 63.6 KB、
   最大的 `app.js` 204 800 B ⇒ 每请求 2 ~ 7 ms 的 zlib）。**补上 `cache_tag` 让这一臂跳到
   66 554.63（68.1×）**，这个选项自己只剩 66 554.63 → 89 791.80（+34.9%）。旧版把
   977 → 89 792 那 91.9× 整个记成了"发孪生省的"，那是归因错了。
2. **两条腿现在几乎重合（+34.9% 对 +34.8%），因为它们的起点终于一样了**。从前
   `uvcpp_web_app` 那条腿是 +67%、`uvcpp_static_server` 是 88×，差这么远不是孪生对两条腿
   价值不同，而是**它们开孪生之前的起点不同**（一条已经压一次缓一次，另一条每请求重压）。
   把 tag 补齐之后这个选项只剩它自己该做的事：**换字节数**，外加省掉那**一次**压缩。
3. **字节那一栏与文件系统无关，也不全是 brotli 省下来的**。盘上 20 个文件共 1 271 603 B，
   其中 15 个有孪生（br 224 029 B / gz 262 407 B，br 比 gz 再少 14.6%），另外 5 个
   webp/woff2 没有孪生、按原样发（101 376 B）—— 即盘上「br + 原样」325 405 B 对
   「gz + 原样」363 783 B，纯带宽那一份是 10.5%。

**一条口径要写在前面**：`precompressed=0` 那一臂发出去的**不是原文件**，是实时 deflate
出来的 gzip —— 它每圈 20 个 URI 送 431 160 B（= 172 463 836 ÷ 400 圈），比盘上那套 `.gz`
孪生（含 5 个无孪生文件共 363 783 B）**还大**。所以别把这张表读成"发原文件 vs 发压缩件"，
它是"**现场压** vs **发盘上那份**"。

**旧版那一节的绝对值（`srv` 的 933.15 → 82 451.28、`app` 的 110 773 → 185 280）不要再引用**：
它们是在更早的树、更早的机器状态下量的，而**同一台机器今天整体慢得多** —— 把 `1.6.18`
那份发布包挂上同一装置、跑同一条孪生命令（那条路与今天**逐字节同策**，只是没有
`cache_tag`），`srv` pc=1 只得 78 174 ~ 79 411、`app` pc=1 得 74 663 ~ 83 365，而当时那一臂
记的是 82 451.28 / 185 280。**跨会话的绝对值在这套装置上不可比，只有同一次会话内的比值可比** ——
这也是本节开头那条口径的真正含义。

> **绝对值与 4.1–4.4 一概不可比**：换机器、换生成器、换并发形状。有意义的是它们本身
> （榜单就是拿这些数打分的），以及 `2xx` / `5xx` 两栏 —— 那是每档的**正确性**事实。

参考机是**单路 AMD Threadripper PRO 3995WX**（Zen 2，64 物理核 / 128 线程，8 通道
DDR4-3200，单 NUMA 节点）。多数档把服务端钉在 `0-31,64-95`（32 个物理核 / 64 个线程，

4. **brotli 这笔钱是什么：每请求重建一次编码器状态，glibc 把内存还给内核，下一个请求再缺页拿回来。**
   这一段全是本机的确定性读数，与平台无关：

   - 库自己的注释（`src/web/uvcpp_http_compress.cpp`，zlib 那个 thread-local `deflate_slot`
     旁边）已经把同一类坑写死了：每请求 256 KB 的分配落在 glibc 的 128 KB `mmap` 阈值之上，

     `json-comp` 那一档上量到 **42 000 → 15 800 rps**。紧接一句是「**这一套在 brotli 上做不到**」，
     理由是 brotli 根本没有 `BrotliEncoderReset()`。⇒ 这条路每请求
     `BrotliEncoderCreateInstance()` / `DestroyInstance()` 一次。

     同一份正文走 gzip 是 497 469 B，最大的块全落在 64–128 KiB 桶里。

     3 次重复与 2 万次请求之内都稳定。

     | `br` 默认 | 72.66 | 522.5 µs |

     | `br` 抬 `MALLOC_MMAP_THRESHOLD_` + `MALLOC_TRIM_THRESHOLD_` | **0.00** | **385.5 µs** |
     | `gzip` 默认 / 同上两个变量 | 0.00 / 0.00 | 261.0 / 262.5 µs |

     只抬 `mmap` 阈值没用（72.66 → 78.63，反而多一点）⇒ 那 700 KB 本来就走堆（glibc 的
     `mmap` 阈值是**动态**的，见过一次 `munmap` 之后自己就升上去），**还回去的是堆顶那次
     `trim`**。两个都抬起来，缺页归零、CPU **−26%**；而 gzip 那一臂两个配置下一动不动

第二轮当时读出来的四条结论（第 2、3 条**已经被 1.7.0 那一轮翻掉**，见上）：

1. **`5xx` 一栏 26 个 `0`。** 这不是运气：两轮之间唯一会成片回 5xx 的那个缺陷（h2 的流被
   套上 h1 的在途上限）在第二轮那版库里已经不在，见下面「第一轮为什么不能当对照」——

### 4.6 JSON 写出器（**第五套装置**，仓外探针）

> 第五套装置：这一节也不在 4.1 / 4.2 的条目上，不是 4.3 的指令数，也不是 4.4 那支静态腿
> 探针。它是一根**只跑序列化**的仓外探针，语料是 HttpArena 的 `data/dataset.json`，形状
> 照着平台 `json-50` 那一档（50 项、整份响应 8 397 B），**不起事件循环、不发包**。所以它
> 量的是**每请求服务端用户态里「把 JSON 变成字节」这一段**，绝对值与任何一节都不可比；
> 有意义的是同一台机器、同一次会话里四个臂之间的差。装置、语料路径与绑核记在
> [`benchmark-rig.md`](benchmark-rig.md) 的「JSON 写出器的量具」一节。

**要回答的问题**：`json-*` 三档要求「每请求用**框架自己的**文档化序列化接口，从活数据
现算现序列化」（预序列化缓存在两种 type 上都不合规）。条目今天走的是
`nlohmann::json::dump()` 一项一项拼 —— 那么这 33 µs 里，**哪些是「序列化」本身、哪些只是
「拼接」**，换成框架自己的流式写出器之后又能吃掉多少？

下表一律写**区间**：每个臂绑核连量 5 轮（`taskset -c 2-3`），同一会话内 5 轮的离散度在
±0.5% 以内，但**两次会话之间还有约 4% 的漂移**（本机是桌面机），所以单点读数不能当真。

| 臂 | 形状 | 50 项响应（5 轮） | 与 A 之比 |
|---|---|---:|---:|
| A 今天的条目 | 每项 `dump()` 后 `append` 进同一个缓冲 | 32.77 ~ 32.91 µs | 1.00× |
| **W 框架写出器** | **`uvcpp_json_writer` 一趟直写，零临时串** | 29.31 ~ 29.90 → **20.66 ~ 20.90** | **1.57 ~ 1.59×** |
| F 手写一趟 | 栈上两位一取的整数表、光标直推预分配缓冲 | 15.50 ~ 16.29 µs | 2.01 ~ 2.12× |
| E 预算串（诊断） | 同一批字节，来自预先算好的每项字符串 | 3.19 ~ 3.42 µs | 9.6 ~ 10.3× |

（「A → W」那一格另有一支臂，把条目今天那份 `build_json` 与新写法**逐字照抄**成两臂同
进程交替量，得到 31.74 ~ 32.01 → 21.29 ~ 21.49 µs，即 **1.49 ~ 1.50×**；与上表 1.57 ~
1.59× 的差就是「同一会话里两支量具本身的 3% 差」，别把任一个当成精确值。）

四条读得出来的结论：

1. **那一项一项的开销里，一大半是「每次调用要跨出去几次 `std::string::append`」，不是
   转义、也不是整数转换。** 框架的 `key()` 原先把逗号、开引号、键体、闭引号、冒号**各
   追加一次**（一项里第一个键 4 次、其余 5 次），字符串值 3 次 —— 于是 8 397 B 的响应共
   **4 073 次** `append_raw`，平均**每 2.1 个字节一次**；每一次都得跨出翻译单元
   （`libstdc++` 的 `_M_append` 带容量检查与 `catch` 子句，内联不进来）。把整段拼在
   256 字节的**栈**缓冲上、再追加一次，同一个响应降到 **1 536 次**，W 因此 29.31 ~ 29.90
   → **20.66 ~ 20.90 µs**（写出器本身 1.42 ~ 1.44×）。
2. **E 的 3.3 µs 是「完全不序列化」的下界**，所以这份响应里 **约 90% 的开销确实是序列化**，
   拷字节与开缓冲加起来只占一成。E **只是诊断**：预序列化缓存正是这条档位规则对
   **两种 type 都**明令禁止的东西，它不是可选方案。
3. **F 与 W 之间还剩约 5 µs，那是「每次调用还剩的那一次 `append`」，也是这个类公开契约的
   价钱。** `str()` / `data()` / `size()` 都是文档化的观测点，实测语义是「凡是成功写进去
   的，都已经在缓冲里」；再往下省只能写进已分配容量、收尾才 `resize`，那会把「一次调用
   中途读缓冲读到什么」变成另一种语义。要更快就得换一套契约，而不是把这一套偷偷改快。
4. **绝对值别横比，也别拿它预言平台分数**：这是**不起服务**的探针数 —— 它数的是 8 397 B
   的序列化，不是任何一档的 RPS。这一节只说「这一段省掉了一小半」；落到平台上值多少，
   要看**下一轮** `json-*` 三档自己的读数。
5. **改条目的那一步是逐字节等价的**：把条目今天那份 `build_json`（每项 `dump()` 后拼接）
   与换成写出器的那份放进同一个进程，在 `n ∈ {0,1,2,7,23,25,40,49,50,999}` ×
   `m ∈ {0,1,2,6,8,11,999999}` 共 70 组上比对，**输出逐字节相同**（n=999 会被夹到 50）。
   这是「换实现不改产物」的直接证据，不靠肉眼读 JSON。

**改动前后的判据**（比上面那张表更该看的）：`tests/functional/json_writer_func.cpp` 原有
867 行**一字未改**，另加 44 行钉住两条快路的边界（42/43 字节那道界、210 字节长键走回落、
「快路按最坏量拒绝、实际却塞得下」仍然成功），同一批断言在**改动前后双双全绿**；输出在
两版上都是 **8 397 B**、逐字节相同。全套 79 条 `ctest` 改动前后逐条**同名同结果**。


### 4.7 缓存校验跑在哪条线程上（**第六套装置**，平台形状 A/B）

> 第六套装置，但**和上面五套都不是同一支**：它用的是 [`benchmark-rig.md`](benchmark-rig.md)
> 「h1/h2 那三档的 A/B」那一节里的靶场 —— 条目裸机起、命令照抄平台、服务端
> `taskset -c 0-7`、驱动器 `taskset -c 8-15`、两臂交替起停（`0 1 1 0`）。与 4.5 的差别
> 只有一处：4.5 是**平台自己的机器**，这里是本机。**两份臂用的是同一个二进制、同一个
> `.so`**，唯一变的是一个环境变量（`UVCPP_ABL_LOOPSTAT=0|1`）⇒ 任何差异都不可能来自
> 构建 / 链接，只可能来自"那次 `stat` 跑在哪条线程上"。

**要回答的问题**：`static-*` 三档的平台每请求 CPU 是 210 ~ 254 µs，而"把字节搬出去"只
解释其中约 30 µs（4.3 节那支 `shaped` 拟合的斜率 × 16 483 B）。命中的请求每一条仍然
要**投一次线程池**，而 4.3 节的 `ab-pool` 读数把池往返 + 池锁争用定在 **18 ~ 36 µs**。
那么，把命中路径上**唯一**需要池的那一步（重新校验用的那次 `stat`）搬回循环线程做，
值多少？——这里量的是**一条腿的每请求用户态 CPU**，不是任何一档的分数。

**判据一（确定性，不吃压测噪声）：`strace -f -c` 下的系统调用计数。** 同一份
`requests/static-h2-uris.txt`，`-m 4 -c 8 -t 4 -n 4000`，两臂各 4000 个 2xx：

| syscall | `POOL` 臂 | `LOOP_STAT` 臂 | 每请求 |
|---|---:|---:|---:|
| `futex` | 18 037 | **929** | 4.51 → **0.23** |
| `statx` | 4 000 | **4 000** | 1.00 → **1.00（一个不少）** |
| `write` | 4 349 | 1 115 | 1.09 → 0.28 |
| 合计 | 29 605 | **7 425** | 7.40 → **1.86** |

（`write` 那一行不解释：响应体走的是 `writev`，这一行两臂都不是发响应的那条路；把它
留在表里是因为"合计"要落到同一批 syscall 上，删掉它会显得总数掉得比实际更多。）

两格各自说明一件事：`futex` 掉到二十分之一是"**池往返没了**"；`statx` 一个不少是
"**校验照样做**，只是换了条线程" —— 后者才是"语义没变"的证据，光看 `futex` 掉是看不出
这一点的。（`ls -l` / `stat` 那类调用在本代 libuv 上走的是 **`statx`**；第一版 trace
列表里没写 `statx`，于是"计数不变"这条判据看上去不成立 —— 那是量具的错，不是库的错。）

**判据二（性能）：平台形状 `-c 256 -m 32 -D 5s`，每个臂三次取中位数**，读
`cpr.sh` 的 `us_per_req`（`/proc/<pid>/stat` 的 utime+stime ÷ 2xx）：

| 腿 | `POOL` | `LOOP_STAT` | 差 | rps（中位数） |
|---|---:|---:|---:|---|
| `h2tls`（`static-h2` 那条腿） | 84.571 µs | **64.671 µs** | **−23.5%** | 83 543 → 122 721 |
| `h1clr`（`static-tls` 那条腿，明文 h1） | 56.084 µs | **39.448 µs** | **−29.7%** | 125 662 → 200 129 |
| `h2c` | 67.667 µs | **46.481 µs** | **−31.3%** | 100 228 → 171 559 |

**中位数是必须的，不是讲究**：六格原始读数里 `h2tls-r1-ls1` 是 95.996 µs、比同臂的另外
两次（62.384 / 64.671）慢了整整 48% —— 每格的第一次（`r1`）在**所有六个序列里都是最慢的
离群点**（桌面机，第一次跑有冷页表与调频）。三个臂六个序列，中位数那一格才是"这台机器
在稳态下给出的数"；把 `r1` 的 95.996 当成 `LOOP_STAT` 的代表，会得出"h2tls 反而变慢"的
反向结论。

**ticks 那一列旁证了同一件事**：`POOL` 三臂是 3 425 ~ 3 582 ticks，`LOOP_STAT` 三臂是
3 971 ~ 4 031 —— 而 8 个核 × 100 Hz × 5 s ≈ **4 000 ticks 就是天花板**。也就是说 `POOL`
那一侧**根本没把绑给它的 8 个核用满**，空转 10 ~ 14%，而省下来的正是"等池"那段；换成
`LOOP_STAT` 直接顶到天花板（这个方向的推论是：再从这里省，得先退出"每请求一次 `stat`"）。

三条口径要一起写：

1. **默认没变。** 新增的是一个选项 `uvcpp_web_revalidate { POOL, LOOP_STAT }`，默认
   **`POOL`**，也就是 1.6.24 之前唯一的行为；`LOOP_STAT` 要显式开。默认那条路上没有新
   代码被走到：`loop_revalidate()` 为假时进的还是原来那个 `else if (cache_enabled())`
   分支，`probe_job` 里按候选键循环的那一段**一行没动**（`git diff` 可逐行核），上面这张表
   的 `POOL` 臂跑的就是它；把 `POOL` 与 `LOOP_STAT` 的 syscall 列并排看也正是这个意思 ——
   两者差在 `futex` 上，`statx` 一格不差。
2. **`LOOP_STAT` 只在本地盘上合算。** 循环线程上那次 `stat` 是**阻塞**的：ext4 上
   1.35 µs、FUSE / 网络盘上 46 µs 量级 —— 后者会把同一条循环上的其它连接一起拖住，
   尾延迟涨而 rps 看着还行。两个数都写在 `uvcpp_web_static.h` 的选项注释里，盘型不明的
   部署继续用 `POOL`（一个字段回退）。
3. **语义逐字不变。** 两种模式下都是"下一个请求必带新字节"：`LOOP_STAT` 走的还是那一份
   `probe_*` + 缓存比对，只是提前到了 `serve()` 里做；`tests/functional/web_app_static_func.cpp`
   新增的 `loop_stat` 用例把这条钉住 —— 改写文件后**第一个**请求就必须拿到新字节
   （孪生 `.br` 被改写后同理），以及一次命中都不许投池。

**别横比**：这三格是**本机 + 单腿 + 一个旋钮**的读数，`us_per_req` 与 4.5 的平台
`(cpu% × 1e6) / rps` 不是一把尺子；这一节只说"这三条腿各少吃掉 1/4 ~ 1/3 的每请求
CPU"，落到平台上是多少，要看下一轮 `static-*` 三档自己的读数。

### 4.8 h3 那条静态腿的同一件事（**仍是第六套装置，换一条腿**）

4.7 量的是 `uvcpp_web_static`（`webapp/` 那份实现）在 **h1/h2** 两条腿上的表现。平台上
还有第三档 `static-h3-64`（QUIC），它走的是**另一份实现** `uvcpp_static_server`
（`web/` 那份，`uvcpp_web_app` 没有 QUIC，h3 上挂静态文件只有这一个选择）—— 所以
4.7 的结论**不能直接搬过去**，得单独量一次。这一节就是那次量测。

**与 4.7 的两处不同，都会改变读数**：

1. 这条腿每请求做的是**两次** `stat`：原文件一次，孪生候选（`app.js.br`）再一次 ——
   20 个 URI 里 15 个有孪生。池往返比 h1/h2 那条腿贵一倍；
2. 但这条腿的每请求 CPU 里有**一大块池往返管不着的**固定开销：QUIC 自己每请求要
   十几次 `sendmsg`/`recvmsg`（下面表里 12.96 + 6.85 = **19.8/req**），那一分钱都省不掉。

**判据一（确定性）：`strace -f -c` 下的系统调用计数。** 平台那条命令照抄
（`h2load --alpn-list=h3 -i requests/static-h2-uris.txt -H "Accept-Encoding: br;q=1, gzip;q=0.8"`），
只把负载压小到量计数够用：`-c 16 -m 16 -t 4 -n 3000`，两臂各 **3000** 个 2xx：

| syscall | `POOL` 臂 | `LOOP_STAT` 臂 | 每请求 |
|---|---:|---:|---:|
| `futex` | 18 830 | **1 984** | 6.28 → **0.66** |
| `statx` | 6 720 | **6 720** | 2.24 → **2.24（一个不少）** |
| `sendmsg` | 38 875 | 38 547 | 12.96 → 12.85 |
| `recvmsg` | 20 543 | 19 420 | 6.85 → 6.47 |
| 合计 | 86 428 | **67 743** | 28.81 → **22.62** |

`statx`/req = 2.24 而不是 1.00，就是上面第 1 条（20 个 URI 里 15 个有孪生 ⇒
`(15×2 + 5×1)/20 = 1.75`，另加每次启动/404 的零头）；**两臂一格不差**才是"校验照样做、
只是换了条线程"的证据 —— 光看 `futex` 掉是看不出这一点的。

**判据二（性能）：平台形状 `-c 64 -m 64 -t 8 -D 5s`，每臂三次取中位数**，读 `cpr.sh` 的
`us_per_req`：

| 臂 | 三次 `us_per_req` | 中位数 | rps（中位数） | ticks |
|---|---|---:|---:|---|
| `POOL` | 121.707 / 125.733 / 131.219 | 125.733 µs | 60 743 | 3 834 / 3 834 / 3 862 |
| `LOOP_STAT` | 116.834 / 125.651 / 117.361 | **117.361 µs** | **68 148** | 4 004 / 4 005 / 4 021 |

每请求 **−6.7%**、rps **+12.2%**。省得比 4.7 那三条腿（−23.5% ~ −31.3%）少，原因就是
开头第 2 条：**这条腿上池往返本来就是每请求 CPU 里较小的一块**。两臂都贴着
8 核 × 100 Hz × 5 s ≈ 4 000 ticks 的天花板（`POOL` 侧 3 834~3 862、`LOOP_STAT` 侧
4 004~4 021），所以这里的 `us_per_req` 差值不是"谁没跑满"，而是同一块 CPU 上少掉的那段
等待 —— 省下来直接换成了多出来的 7 400 rps。

**判据三（尾延迟，4.7 的风险 3 在这里复核）。** 循环线程上就地 `stat` 会阻塞同一条
循环，最坏情况是"rps 看着还行、p99 爆掉"。两臂各多跑一轮（同样的形状），加上
h2load 的 `--log-file` 拿逐请求耗时，只统计 2xx：

| 臂 | 请求数 | p50 | p90 | p99 | max |
|---|---:|---:|---:|---:|---:|
| `POOL` | 290 387 | 63 661 µs | 109 708 µs | 170 526 µs | 358 108 µs |
| `LOOP_STAT` | 337 305 | **56 896 µs** | **86 938 µs** | **140 458 µs** | **307 201 µs** |

尾延迟**变好而不是变坏**：这台机器上语料在 ext4（`/tmp`）上，一次 `stat` 是微秒级，
挪到循环线程省下的那次池往返比它本身贵。⇒ 4.7 的风险 3（"p99 涨 >2× 即证伪"）**没有被
证实**。**但这只说明本地盘这一档**：FUSE / 网络盘上一次 `stat` 是 46 µs 量级，那条路上
同一个旋钮的结论要反过来读（`uvcpp_static_server.h` 的选项注释里两个数都写着），
所以默认档仍是 `POOL`。

三条口径与 4.7 逐字相同，只是换了一份实现和一个类名：**默认没变**（`uvcpp_static_revalidate`
默认 `POOL`，老调用方一行不改）、**`LOOP_STAT` 只在本地盘上合算**、**语义逐字不变**
（两种档都是"下一个请求必带新字节"）。第三条由
`tests/functional/web_static_server_func.cpp` 新增的 `loop_stat` 用例钉住 —— 它除了逐字节
比对七种请求形状（孪生 / 目录 index / 目录步进 / SPA 回退，含那两跳递归）之外，还读**处理函数
返回之后**的 `resp.deferred`：命中与 404 必须是 `false`（就地回完），只有真的落到读盘
那条路才是 `true`。这一格是两档**唯一**不同的地方，也正是"搬回循环线程"这句话的
可执行版本。

**别横比**：这里的 `us_per_req` 与 4.7 那三格**不是同一份实现**（`uvcpp_static_server`
对 `uvcpp_web_static`）、也不是同一条传输，逐格对照没有意义；两节各自只说"自己那条腿
少吃掉多少每请求 CPU"。

### 4.9 命中路径不再整块拷贝（**h3 那条腿 + callgrind 装置**）

> 又是两套装置的拼装：服务端与形状同 4.8（h3 那条腿、`--alpn-list=h3`、`-c 16 -m 64
> -t 8 -D 20s`），读数取 4.3 的 callgrind（每请求指令数）。两臂是**同一个条目二进制、
> 同一份环境**，只换 `LD_LIBRARY_PATH` 指的那份 `.so`：`so-head` 用本改动**之前**的
> `src/web/uvcpp_static_server.cpp` 建，`so-share2` 用改完那份建。**绝对值与 4.3 那张表
> 不可比**（那条腿是 h1 + `gcannon`），跟 4.7 / 4.8 的 µs 也不可比。
>
> **为什么连接数不是 64**：先用平台形状 `-c 64 -m 64 -t 8 -D 5s` 跑了一轮，只有 **136**
> 个 2xx，而 callgrind 表头两位是 `rsaz_1024_sqr_avx2`（36.9%）与 `rsaz_1024_mul_avx2`
> （10.7%）—— 那是**握手的 RSA**：64 条连接各握一次手，摊在 136 个请求上。把连接数压到
> 16、窗口拉到 20 秒之后，握手那两项在两臂里变成**绝对值逐条相同**（`rsaz_1024_sqr_avx2`
> 两臂都是 69 481 344 条），于是它从干扰项变成了对照组。

| 读数（`--alpn-list=h3 -c 16 -m 64 -t 8 -D 20s`） | 2xx | part 2 指令合计 | **每请求指令数** |
|---|---:|---:|---:|
| 改动前（`so-head`） | 5 847 | 1 408 228 282 | 240 846.3 |
| 改动后（`so-share2`） | 6 087 | 1 274 849 946 | **209 438.1** |

⇒ 同一会话内夹逼 **−31 408.2 条/请求（−13.04%）**。

逐函数归因（每请求；`Δ` 那一列是"新 − 旧"）：

| 函数（每请求） | 前 | 后 | 差 |
|---|---:|---:|---:|
| `__memcpy_avx_unaligned_erms` | 72 306.3 | 41 000.8 | **−31 305.5** |
| `malloc` | 3 441.2 | 2 824.9 | −616.3 |
| `_int_free` | 4 919.4 | 4 642.1 | −277.3 |
| `free` | 2 068.7 | 1 931.2 | −137.5 |
| `_int_malloc` | 3 574.9 | 3 543.1 | −31.8 |
| `_aesni_ctr32_ghash_6x`（对照：TLS 那点每字节成本没动） | 29 669.1 | 29 744.7 | +75.6 |
| `rsaz_1024_sqr_avx2`（对照：绝对值两臂相同） | 11 883.2 | 11 414.7 | −468.5（纯分母效应） |
| `_Rb_tree_increment`（反例，见下） | 5 683.4 | 6 180.9 | **+497.5** |

**总量的 99.7% 就是 `__memcpy` 那一行。**

#### 这一节真正该记下来的东西：callgrind 的 `rep movsb` 是**按字节**计费的

上表那个 −13.04% 看上去像"提速 13%"，**它不是**。同一台机器上标定一次就清楚了：

| 标定项 | 读数 |
|---|---|
| 真机 `memcpy` 16 483 B（源在 L2、20 万次、`-O2`） | **73 ~ 80 ns / 次**（215.5 / 227.3 / 207.0 GB/s） |
| 同一段代码放进 callgrind | **16 515 条 Ir / 次**（= 16 483 字节 + 32 条循环开销） |

也就是说 callgrind 把 glibc 的 `memmove-vec-unaligned-erms`（走 `rep movsb`）记成
**每条 Ir 搬运一个字节**，而真机上 16 KB 只要 75 ns（≈215 GB/s，比它"便宜"三个数量级）。
于是那 −31 305.5 条/请求要**先除以字节数才能读**：**31 305.5 ÷ 2 = 15 652.8 B**，正好是
一次响应体的平均字节数 —— 与语料侧 8 000 次请求 131 865 720 B ⇒ 16 483 B/请求（减去
~830 B 的帧与头）对得上。**这一行读作"两次整块拷贝没了"，不能读作"少了 13% 的时间"。**
折成时间：两次 15 653 B 的 `memcpy` ≈ **0.14 µs/请求**，再加省掉的那一次 16 KB
`malloc`/`free`（分配器那一簇每请求共 −1 095 条 Ir），合计 **~0.2 µs**。

⇒ **这一格在 µs 腿上是分辨不出来的**，表就照实贴着、但**不作为证据**：

| 臂 | `us_per_req`（平台形状 `-c 64 -m 64 -t 8 -D 5s`，三轮） | 中位 |
|---|---|---:|
| 改动前 | 116.414 / 123.594 / 124.342 | 123.594 |
| 改动后 | 119.094 / 119.401 / 118.294 | 119.094 |

两臂的 **CPU tick 总量几乎一样**（旧 3 982 / 4 016 / 4 002，新 4 013 / 4 013 / 4 006；8 个核
跑满 5 秒约 4 000 tick），2xx 数的差（旧 321 854 ~ 342 056、新 336 961 ~ 338 647）与轮内散度
同量级 —— 轮内散度 **6.8%**，而被测效应是它的 **1/40**。表里那点"差"是噪声。
（`_Rb_tree_increment` 反而涨了 497.5 条，也是同一件事的旁证：两臂的**混载不是逐字相同的**
—— 快的那一臂在同一个 20 秒窗口里多服务了 4.1% 的请求，于是"随在途流数增长的项"跟着涨。）

#### 确定性判据：指针同一

发出去的字节两种实现**逐字节相同**，所以这件事在网络上、在任何字节比对里都看不出来。
判据只能落在库内部：`test_web_static_server_func` 的 `loop_stat` 用例多了第 8 条 ——
再命中一次 `/app.js` 时，`resp.body` 必须与第 2 条**指向同一个 `std::string`**
（读 `is_shared()` 与 `shared_ref().get()`）。本条改动前那版源码里，两次命中各有各的
`std::string`，指针**不可能**相等。

变异测试：把命中路径改回"先造一份临时响应、再整块赋给调用方"（`ok()` + `out = tmp`），
**6 条断言变红**（第 1 / 3 / 5 / 6 / 7 条的 `body.is_shared()` 为假、第 8 条指针不等），
变异版退出码 **2**、还原版 **0**。

两条配套的机制，都写在头文件注释里、这里只记结论：`uvcpp_buf` 的拷贝构造**是深拷贝且
丢共享态**，而 `uvcpp_http_response` 手写了拷贝构造 / 拷贝赋值 / 析构 ⇒ **没有隐式移动**，
`std::move(resp)` 在类型上就退化成一次深拷贝 —— 这正是改动前那条路上那两次整块拷贝的
来源，也是"共享视图遇到一次拷贝就白共享了"的机制（所以 `get_data()` / `get_udata()`
会 `materialize()`）。

#### 结论（以及它对下一刀的影响）

本条**不是提速**，是"命中路径不再每请求重演一遍整块拷贝 + 少一次 16 KB 分配"：
~0.2 µs/请求（~0.2%）。它值得单独一条提交是因为判据是**确定性**的、语义逐字不变。

真正的信息在反面：**h3 腿的每请求指令数里，`memcpy` 占 19.6% 却几乎不花时间**
（按字节计费的坑），而分配器那一簇 **14 187 条/请求（6.8%）**、AES-GCM/QUIC 每字节那条
路径（`_aesni_ctr32_ghash_6x` **29 745 条/请求**）才是真花钱的地方。⇒ 下一刀砍分配器与
那条每字节路径，**别**继续找"还剩几次整块拷贝"（4.3 那种"`memcpy` 占比最高"的画像在这台
机器上会骗人）。

**补正（2026-10-13，写 4.10 时回头加上）**：上面这句「别继续找还剩几次整块拷贝」是
**就 h3 那条腿**说的，在那条腿上成立 —— h3 腿剩下的整块拷贝是每请求 2 次 ≈ **0.2 µs**，
确实不值得追。**它不能外推**：同一类"整块拷贝"在 h2 两条腿上是响应体的 **4.56× 与 11.17×**，
砍掉其中 40.7 KB/请求换来的是 µs 腿上干净的一格 **−7.4%**（4.10）。⇒ 正确的说法要**分腿**：
h3 腿上拷贝不是问题（那儿的问题是 AES-GCM 与分配器），h2 腿上拷贝**就是**问题。


### 4.10 静态腿的大头：TLS 出口每批两遍整块拷贝（**第七套装置**，`LD_PRELOAD` 精确计费）

> 服务端与混载形状同 4.8 的 h2 支线（20 文件、`-m 32 -c 256 -t 8 -D 5s`），但**读数既不是
> rps 也不是指令数**，是 `memcpy` / `memmove` / `memset` 的**精确计费**（调用次数 + 字节数，
> 按**调用点**分组）。两臂是同一个条目二进制、同一份环境，只换 `LD_LIBRARY_PATH` 里那份
> `libuvcpp.so`。**绝对值与 4.3 / 4.7 / 4.8 / 4.9 都不可比。** 装置与协议记在
> [`benchmark-rig.md`](benchmark-rig.md) 的「用户态拷贝的量具（`memspy`）」一节。

#### 先修装置：上一轮采样器那 34% 是个**假名字**

上一轮用的采样器（`prof.py`：定时抓 PC → 按 `/proc/<pid>/maps` 折成「模块 + 偏移」→ 取该模块里
**最近的前一个符号**）在 h2 两条腿上排第一的都是同一个东西：

| 腿 | 采样器排第一的符号 | 占比 |
|---|---|---:|
| h2 明文 | `libc.so.6:__nss_database_lookup@GLIBC_2.2.5` | 34.16% |
| h2+TLS | `libc.so.6:__nss_database_lookup@GLIBC_2.2.5` | 34.10% |

`__nss_database_lookup` 是 NSS 的名字服务查找，静态腿一次都不该碰到它。真凶是
**`memcpy`/`memmove` 的真实现**（`__memmove_avx_unaligned_erms`）：

| 读数（`ifn2`：读 `/proc/self/maps` 自己算偏移，**不走 `dladdr`**） | |
|---|---|
| `memcpy` 的真实现 | `libc+0x188a80` |
| `memmove` 的真实现 | `libc+0x188a80`（同一个） |
| 它**前面**最近的一个**导出**符号 | `__nss_database_lookup` `libc+0x188040`（相隔 **2 624 B**） |
| 它**后面**下一个导出符号 | `_thread_db_dtv_slotinfo_list_slotinfo` `libc+0x1c5d58` |

⇒ 两者之间是 **247 KiB 没有任何导出符号**的 `.dynsym` 空洞：glibc 把 `memcpy`/`memmove`/`memset`
的 AVX/ERMS 实现放在那里，`.dynsym` 里只留 `memcpy@GLIBC_2.14` 那一类 IFUNC 间接入口。
于是**任何**"最近前一个符号"的解析都会把这一整簇记到 `__nss_database_lookup` 头上：
**数字是对的（用户态拷贝确实占三成多），名字是假的。**
（顺带解释为什么绕不过去：`dlsym(h, "memcpy")` 会**直接穿到**真实现，拿到的是地址不是名字 ——
只能自己算 `maps` 偏移，这就是 `ifn2` 存在的理由。）

采样器还有第二个毛病：它只说得出"**在**拷贝"，说不出"**是谁**发的"。要动刀就得知道
每一字节是哪一行代码拷的。所以这一节换装置。

**装置 `memspy`**（`LD_PRELOAD` 一个 `.so`，**精确计费，不是采样**）：

- 拦 `memcpy` / `memmove` / `memset` / `__memcpy_chk`；
- 按 **`__builtin_return_address(0)`** 分组 —— 分组键是**调用点**，不是被调函数；
  16 384 槽开放寻址表，无锁 CAS 插入（多线程下不丢样本）；
- 每组记 **调用次数 / 总字节 / 四个尺寸档**（`<64` / `<1K` / `<16K` / `≥16K`）；
- `SIGUSR2` 或析构时 dump，前面附一份带 `MSPY_MAP ` 前缀的 `/proc/self/maps`，
  离线用 `resolve.py` 折成「模块 + 符号 + 偏移」。

**它自己的盲区，先说在前面**：GCC 对**编译期长度已知**的小 `memcpy` 会内联成几条 `mov`，
**不经过 `memcpy`** —— 哪怕 `-O0`。自测里 1000 次 16 字节**常量**长度的拷贝**一次都拦不到**，
而同样 16 字节、长度取自运行时的循环全拦到了。⇒ 这张表的**大块是准的**（16 KB 级不可能被内联），
**小碎块会系统性漏**。所以下面只用它读 `≥16K` 那一档，小字节数不参与结论。

#### 同一份工作，三条腿

平台 static 那三档发的是**同一批 20 个文件**，但传输层与实现都不同。同形状各跑 5 秒：

| 腿 | 2xx | `memcpy`/`memmove`/`memset` 总量 | 每请求 | ÷ 响应体 16 483 B |
|---|---:|---:|---:|---:|
| h1 明文（`:8080`） | 347 595 | **942 303 166 B（0.94 GB）** | 2 711 B | **0.16×** |
| h2 明文（`:8082`） | 331 881 | **24 931 603 581 B（24.93 GB）** | 75 122 B | **4.56×** |
| h2+TLS（`:8443`） | 301 863 | **55 584 900 823 B（55.58 GB）** | 184 141 B | **11.17×** |

⇒ 同一份工作，**h2+TLS 比 h1 多搬 59 倍字节**、每请求多搬 **181 KB**；连 h2 明文都已经
是响应体的 4.56 倍。而 h1 那条腿证明**这件事是可以不做的**：它的交付路径
（`uvcpp_tcp_client::write_owned`，370 174 次调用 / 107.4 MB / 均 290 B）**≥16 KB 的拷贝是 0 次**
—— 16 KB 的响应体是**把所有权交给 `uv_write` 走的**，一字节都没拷。

#### 谁在拷：h2+TLS 的逐调用点归因（改动前）

| 调用点 | 调用 | MB | 均 B | ≥16K | 占比 |
|---|---:|---:|---:|---:|---:|
| `std::string` 内部（libstdc++ `0x16872f`） | 1 792 543 | 14 215.8 | 7 930 | 119 077 | 25.6% |
| `std::string` 内部（libstdc++ `0x16a024`） | 7 605 509 | 7 847.3 | 1 032 | 370 739 | 14.1% |
| **`uvcpp_tcp_client::tls_flush_out`（`0x288658`）** | **19 938** | **5 015.6** | **251 562** | **14 665** | **9.0%** |
| OpenSSL 内存 BIO 输出侧（`0x469405`） | 326 462 | 5 025.4 | 15 394 | 295 806 | 9.0% |
| OpenSSL 内存 BIO 输入侧（`0x468eb1`） | 357 225 | 5 025.3 | 14 068 | 295 811 | 9.0% |

**`tls_flush_out` 那一行是靶心**：19 938 次调用、每次 **251 562 B**（= 一批密文）、
14 665 次落在 `≥16K` 档 —— 一次调用把**一整批 TLS 密文**从 `tls_out_` 拷进一个新 `uvcpp_buf`，
只为交给 `uv_write`。两个 `std::string` 站点（`0x16872f` 与 `0x168755`）里 `≥16K` 的那一档
（119 077 与 109 156 次、均 ~114 KB 与 ~16 KB）则是**同一批密文在 `tls_out_` 上按 2 倍几何增长
时被反复搬运**的痕迹 —— 16 KB 那个均值正是几何级数里最小的那几步。

其余四行（OpenSSL 内存 BIO 两个方向 + `WPACKET_close` + `BUF_MEM_grow_clean`，各 ~5 GB、
各 ~30 万次 `≥16K`）是**架构性**的：`uvcpp_tls` 把 OpenSSL 的读写 BIO 接在内存缓冲上，
每字节密文因此在用户态多走两趟；`cb_read_body` 是 nghttp2 的数据提供者，每次回一个 16 KB 分片。
这两类**本轮不动**。

#### 修：`reserve` 一次到位 + 整批当共享视图交出去

`tls_flush_out()`（`src/net/uvcpp_tcp_client.cpp`）原来两处各拷一遍：

```cpp
// doc-snippet: fragment — 摘录改动前后的两处，省略号处不是完整翻译单元
char buf[16384]; size_t n;
while ((n = tls_ssl_->take_ciphertext(buf, sizeof(buf))) > 0)
  tls_out_.append(buf, n);                        // ① 从 0 长到 250 KB，每批 2 倍几何增长
...
std::string chunk; chunk.swap(tls_out_);
uvcpp_buf bufcpp(chunk.data(), chunk.size());     // ② 整批再拷一遍，就为了交给 uv_write
```

改成：

```cpp
// doc-snippet: fragment — 同上，摘录
const size_t pend = tls_ssl_->pending_ciphertext();       // 这批多少字节，OpenSSL 自己知道
if (pend > 0) tls_out_.reserve(tls_out_.size() + pend);   // ① 一次分配，零次搬运
...
auto chunk = std::make_shared<std::string>(); chunk->swap(tls_out_);
w->append_uv_buf_view(uv_buf_init(chunk->data(), chunk->size()), chunk);   // ② 借出去
```

用 `reserve` 而不是 `resize` 是有意的：`resize` 会把新露出的那段**清零**，等于每批白清 250 KB。
`append_uv_buf_view()` 是写层**已有的**零拷贝通道（`hold_` 持着 `shared_ptr`、析构时放掉），
`uvcpp_h2_connection::flush()` 的 TLS 支线已经在用同一个机制（`write_buf_->share(pending)`；
明文那条支线在 §4.11 里并到同一条路上）。

#### 确定性判据：每请求拷贝字节（三臂，含一个变异）

同一个 5 秒形状。`t1` = 上面改完那份；`t2` = **只把 `reserve` 那两行去掉、视图保留**的变异臂：

| 臂 | 拷贝总量 | 2xx | **每请求** | 相对 `t0` |
|---|---:|---:|---:|---:|
| `t0` 改前 | 55 584 900 823 B（55.58 GB） | 301 863 | 184 141 B | — |
| `t2` 变异：只要视图、不要 `reserve` | 49 791 493 701 B（49.79 GB） | 297 012 | 167 641 B | −16 500 B（−9.0%） |
| `t1` 改后 | 44 539 030 319 B（44.54 GB） | 310 462 | **143 461 B** | **−40 680 B（−22.1%）** |

这个数**可复现**：另换一轮跑，`t1` 是 42 445 575 223 B ÷ 296 763 = **143 029 B/请求**（−22.3%）
—— 两轮差 0.3%，比任何 µs 读数都稳，所以它够格当判据。

变异臂把两半**分开**了：

- **视图那一半 ≈ 16.5 KB/请求**（`t0 − t2`）。这个数正好是**一次响应体**（16 483 B）的量级：
  一批 251 562 B 的密文摊到约 **15 个请求**上，摊到每请求就正好一个 body。
- **`reserve` 那一半 ≈ 24.2 KB/请求**（`t2 − t1`）。方向也对：几何增长搬的总字节
  ≈ 2 × 终值 × 批数，摊到每请求是 1.5~2 个 body。

两个**互相独立**的确认：

1. `t1` 的归因表里 **`tls_flush_out` 这个调用点整个消失**（`--top 200` 都搜不到）——
   两臂之间唯一的差别就是它不再拷了。
2. `t0` 里那两个 `std::string` 站点 `≥16K` 档的次数（119 077 / 109 156）在 `t2` 里
   **原样回来**（114 859 / 106 468），在 `t1` 里掉到 **53 791 / 39 255**。

#### µs 那条腿：交错三轮，82.1 → 76.0 µs

拷贝字节是判据，时间只当旁证。同形状，`t0` / `t1` **交替**跑、各 3 次：

| 臂 | 三轮 `us_per_req` | 中位 |
|---|---|---:|
| `t0` | 79.869 / 88.258 / 82.068 | 82.1 |
| `t1` | 73.848 / 77.347 / 75.970 | **76.0** |

⇒ **−6.1 µs（−7.4%），3–0，两臂区间无交叠**（`t0` 最低 79.9 > `t1` 最高 77.3）。
40 680 B/请求 ÷ 6.1 µs = **6.7 GB/s** —— 与 4.3 那条 0.16 ns/B（≈6.2 GB/s）的标定落在同一个带里
（省下的还有几何增长那一串 `malloc`/`free`，所以 6.7 是**有效**速率，不等于 `memcpy` 带宽）。

**先记一个自己踩的坑**：第一次跑的是**非交错**两臂（`t0` 全跑完再跑 `t1`），读出来
h2+TLS 是 125.388 → 126.903 µs，看着像 **+1.2% 的倒退**。但同一轮里两条**负对照**也各涨了
+1.6%（h2 明文）与 +1.0%（h1 明文）—— **三条腿一起涨同样的幅度，涨的是机器不是代码**。
改成交错之后，负对照回到一动不动、被测腿掉 7.4%。

#### 负对照：另外两条腿一字节都没动

| 腿 | `t0` | `t1` | 判读 |
|---|---:|---:|---|
| h1 明文 | 942 303 166 B | **942 303 166 B** | **逐字节相同** |
| h2 明文 | 24 931 603 581 ÷ 331 881 = 75 122 B/请求 | 24 660 639 621 ÷ 325 835 = 75 686 B/请求 | +0.75%，噪声内 |

机制上也说得通：`tls_flush_out()` 第一行就是 `if (tls_ssl_ == nullptr) return;`，
h1 / h2 明文两条腿**根本不进这个函数**。

#### 下一刀

h2 明文那条腿的 `uvcpp_h2_connection::flush()` 是同一件事、同一个形状：21 924 次调用、
均 **251 595 B**，占 h2 明文全部拷贝字节的 **22.1%** —— 它就是本节的 `tls_flush_out`
在那条腿上的对应物，只不过那条腿没有 TLS，走的是明文支线的整块拷贝
（`write_buf_ = new uvcpp_buf(pending->data(), pending->size())`）。它**不是 TLS 专属**的，
所以两条腿都能吃到；难点在明文支线今天用 `out_uv_buf()` **接走块的所有权**，
共享视图到那一步会被 `materialize()`，得先把这条交付路径也改成收视图。**§4.11 就是这一刀。**

### 4.11 同一个形状在 h2 明文那条腿：交付路径收视图，`flush()` 的两条分支合并（**仍是第七套装置**）

#### 卡在哪一步

`uvcpp_h2_connection::flush()` 把 `out_` **换**进一份 `shared_ptr<std::string>`（零拷贝），
但交给写层的方式按连接形态二选一：TLS 支线走 `write_buf_->share(pending)`（视图），
明文支线走 `new uvcpp_buf(pending->data(), pending->size())`（**整块拷一遍**）。
明文这一支不能直接照抄 TLS：`uvcpp_tcp_client::write(uvcpp_buf*, cb)` 无条件
`buf->out_uv_buf()` **接走块的所有权**，而 `out_uv_buf()` 对共享视图会先 `materialize()`
—— `uvcpp_buf.h` 自己在那一段写着"它不是错误，是一次白拷贝"。

所以顺序是：**先让交付路径认视图，再合并分支**。判据是 `uvcpp_buf::is_shared()`，
和 `uvcpp_write::adopt_body()`（`src/req/uvcpp_write.cpp:130`）已经在用的**同一条规则**：

```cpp
// doc-snippet: fragment — 摘录 `uvcpp_tcp_client::write(uvcpp_buf*, cb)` 的交付段
uvcpp_write* w = new uvcpp_write();
if (buf->is_shared()) {                       // 共享视图：借出去，别 materialize
  w->append_uv_buf_view(uv_buf_init(const_cast<char*>(buf->get_const_data()),
                                    static_cast<unsigned int>(buf->size())),
                        buf->shared_ref());
} else {
  w->set_uv_buf(buf->out_uv_buf(), true);     // 自有块：照旧接走所有权
}
```

`get_const_data()` 就是 `return this->buf.base;`（`uvcpp_buf.cpp:378`），**不物化**；
`const_cast` 在 C++11 下是必需的（非 const `std::string::data()` 仍返回 `const char*`）。
顺带把这次写的两处 `get_uv_buf()` / `1` 换成 `get_uv_bufs()` / `get_uv_nbufs()`，
于是单块与双块两条路径走同一个出口。改完 `flush()` 的这一段只剩：

```cpp
// doc-snippet: fragment — 摘录 `uvcpp_h2_connection::flush()` 的交付段，改后
std::shared_ptr<std::string> pending = std::make_shared<std::string>();
pending->swap(out_);
write_buf_ = new uvcpp_buf();
write_buf_->share(pending);                   // 两种连接形态同一条路，都不再拷
```

- **视图存活**：借出去的那块由 `uvcpp_write` 持有的引用计数履行，`flush()` 返回、

### 4.12 h2 两条腿的 `out_`：每批从 0 开始几何增长 → 按上一批大小 `reserve`（**仍是第七套装置**）

#### 机制：容量每批都被搬走

`uvcpp_h2_connection::flush()` 走的是 `drain(out_)` —— 而 `drain()` 是把本批帧
**一段一段 `append` 进 `out_`** 的（`nghttp2_session_mem_send2` 每返回一帧就追加一次），
下一句 `pending->swap(out_)` 又把整批**连缓冲区一起**取走交给写层。于是 `out_` 每批都从
`capacity() == 0` 重新开始，按 2 倍几何增长，搬的总字节 ≈ 2 × 终值，再摊上十几次
`malloc`/`free`。

修法是给 `out_` 一个**跨批的容量提示**：同一个连接上批与批高度相关，上一批的大小就是
这一批免费的预测。

```cpp
// doc-snippet: fragment — 摘录 `flush()` 里 reserve 提示的设置点
if (out_hint_ > 0) out_.reserve(out_.size() + out_hint_);   // 一次分配，零次搬运
const int rv = session_->drain(out_);
...
out_hint_ = (pending->size() <= (1u << 20)) ? pending->size() : 0;   // 超过 1 MiB 就不再提示
```

两点**不是**顺手写的：

- **这个提示不会把内存钉在连接上**。`out_` 的缓冲区每批都被 `swap` 进 `pending` 交给
  写层，函数返回时 `out_` 的容量已经回到 0 —— 也就是说这份预留是**一批的生命周期**，
  与改动前的峰值同一个量级。
- **上限 1 MiB** 是为了不让某一次异常大的批把**此后每一次** flush 都撑到那个尺寸
  （退化方向是"回到几何增长"，只会变慢不会变错）。

#### 确定性判据：每请求拷贝字节（两条被测腿 + 一条负对照）

同一个 5 秒形状，`t3` = §4.11 之后那份，`t4` = 本次改后：

| 腿 | `t3` | `t4` | 判读 |
|---|---:|---:|---|
| h2 明文 | 19 410 751 545 ÷ 333 624 = 58 181.5 B | 19 073 238 810 ÷ 336 849 = **56 622.5 B** | **−1 559 B（−2.7%）** |
| h2+TLS | 43 128 475 016 ÷ 301 886 = 142 863.4 B | 43 368 888 691 ÷ 307 601 = **140 990.7 B** | **−1 873 B（−1.3%）** |
| h1 明文（负对照） | 2 701.6 B | 2 706.8 B | +0.19%，噪声内 |

这一刀与 §4.11 不同：**两条 h2 腿都该掉**，因为两条腿的明文侧都要过 `drain(out_)`
（TLS 只在 `tls_flush_out()` 之后才分岔）。负对照依旧不该动，h1 那条腿根本不进
`uvcpp_h2_connection`。

#### 归因表：确实是从 `0x16872f` 那一行抠下来的

| 量 | `t3` | `t4` |
|---|---:|---:|

- **`0x16872f` 剩下的部分**按上面的证伪**重新归因**（它已经明确不在 `out_` 上）。


### 4.13 静态腿的路径解析不再每请求重来（**第八套装置**，`LD_PRELOAD` 数系统调用）

#### 机制：每个请求一次 `realpath`，而它是一条逐分量的 `lstat`

`uvcpp_web_static` 判"这个落点在不在文档根内"用的是
`web_resolve_within_root()` —— 它必须展开符号链接，所以每个请求都少不了一次
`realpath`。`realpath` 在 glibc 里是**沿路径逐分量 `lstat`**（而且那些 `lstat`
走的是库内部符号，外部探针看不见），于是它是这条热路径上最大的一笔文件系统开销。

修法是把上一次的解析结论记下来：展开后的绝对路径 `fs_path` 加上
`(st_dev, st_ino)`。命中时只做**一次 `stat`** 比对指纹，不再 `realpath`。
关键的一步是**负数结论也要记**：没有孪生文件的资源每请求都要试
`url + ".br"` / `url + ".gz"` 这两个**注定失败**的候选，只记正数的那一版实测
`realpath`/请求只掉到 0.980。

```cpp
// doc-snippet: fragment — 摘录 `probe_leaf()` 的快路径（省略负数分支）
const resolve_hint* h = find_hint(cfg.resolve_memo ? hints : nullptr, url);
if (h != nullptr) {
  if (h->exists) {
    uint64_t dev = 0, ino = 0;
    if (stat_real(loop, h->fs_path, out.is_dir, out.mtime_sec, out.mtime_nsec,
                  out.size, &dev, &ino) && dev == h->dev && ino == h->ino) {
      out.fs_path = h->fs_path;      // 指纹没变 ⇒ 当初"在根内"的判断仍然成立
      out.status = probe_status::OK;
      return out.status;
    }
  }
  ...
}
```

#### 确定性判据：每请求的文件系统系统调用次数（三臂）

`strace` 在这台机器上用不了（`ptrace` 被禁），而且它自己的减速会改变量到的形状。
这里用的是 `LD_PRELOAD` 一个探针：拦 `syscall()` 并解出 `SYS_statx` /
`SYS_newfstatat` / `SYS_openat` / `SYS_readlinkat`，另外拦 `lstat`/`stat`/`readlink`/
`realpath`。**glibc 的 `realpath` 内部走的是 `__lstat64`/`__readlink`，外部拦不到**
（实测：单独跑 1000 次 `realpath`，其余计数器全 0）—— 它便宜不了，只是这把它量的是
**调用次数**而不是它内部的 `lstat` 次数，这一点写在口径里。

同一个入口二进制、只换 `libuvcpp.so`，先 4000 请求热缓存，窗口 20 000 请求、每臂
两轮（20 个 URL 的混载，`-c 256 -m 32`，ext4 语料）：

| 臂 | 库 | 入口 `resolve_memo` | `realpath`/req | `statx`/req | 小计/req |
|---|---|---|---:|---:|---:|
| C（改动前的整对） | 旧 | — | 2.734 / 2.734 | 2.245 / 2.245 | 4.994 / 5.033 |
| D | 新 | `true`（默认） | **0.001 / 0.001** | 2.245 / 2.245 | **2.285 / 2.272** |
| E | 新 | `false` | 2.734 / 2.734 | 2.245 / 2.245 | 5.013 / 4.993 |

E 是**关掉那个开关**的同一份库，它逐列等于 C ⇒ "关掉 = 回到不做记忆时"是量出来的。
`statx` 一模一样是设计如此：慢路径本来也要 `stat` 一次拿 mtime/size，快路径那次
指纹 `stat` 是把它**换掉**而不是加上去。

#### 这些数还对得上一个按 URL 拆开的模型

只放一个 URL 的请求表再量一遍：带孪生文件的（`app.js`）是 `2 realpath + 2 statx`，
没有孪生的（`bold.woff2`）是 **`5 realpath + 3 statx`**。多出来的那几次不是噪声 ——
`web_real_path(allow_missing=true)` 在整条路径 `realpath` 失败之后**还要再解析一次
父目录**（`src/webapp/uvcpp_web_util.cpp:854-854`、`src/webapp/uvcpp_web_util.cpp:871-871`），所以一次**失败**的解析是 2 次 `realpath`
而不是 1 次。加权 `(15×2 + 5×5)/20 = 2.75` 对 `(15×2 + 5×3)/20 = 2.25`，与上面
实测的 2.734 / 2.245 对上（差的那点是混载里连接建立期的零头）。

#### 变异：把指纹比对去掉，必须红在**内容**上

`test_resolve_hint()` 把 `/hintdir/a.txt` 正常服务一次（烧进记忆），然后把
`/hintdir` 换成**指向根外的链接** —— 路径文本一个字都没变。把
`(dev == h->dev && ino == h->ino)` 改成恒真之后：**2 条红**，其中一条是
`响应体里出现了 [OUTSIDE-AFTER-DIR-REPOINT]`，也就是说根外那个同名文件的字节真的
发出去了。这正是这条判据必须落在内容上的原因：只比状态码的话，"换向没换成功"与
"挡住了"给出的都是非 200。

#### µs：这台机器分辨不出来，只声称"没劣化"

平台 static-h2 形状（`-c 1024 -m 32`）按 C D E E D C 的顺序各跑 4 轮取中位数：

| 臂 | `us_per_req`（中位数） | 四轮的散度 |
|---|---:|---|
| C | 92.2 µs | 82.5 – 97.9 |
| D | **87.9 µs** | 84.2 – 89.7 |
| E | 98.1 µs | 91.3 – 101.4 |

D 最低，但**同一臂内部的散度（±8%）比臂间差还大**（C 的四轮从 82.5 抖到 97.9）。
2.73 次 `realpath` 在 ext4 上按 §4.4 的单文件消融折算只有几微秒量级，正好落在这台
机器在这个形状上的噪声底线以下。所以能声称的只有"没劣化"，判据仍然是上面那张
系统调用表。

#### 已知且接受的一处行为差异

路径的落点被整体搬到根外、原位留下一个指向**同一个 inode** 的链接时
（`mv` 到根外 + `ln -s` 回原位），指纹不变 ⇒ 命中路径继续按原 URL 服务它，而完整
解析会判越界。差别是"曾经被授权过的那份字节多活一会儿"，不是读到没被授权过的字节：
`rm` 立即生效，`validate.sh` 的 staleness 探针用 `mv -f` 换文件（inode 必变）也不
受影响。要绝对严格就把 `resolve_memo` 关掉（一个字段，代价回到 C 那一行）。

#### 下一刀

`statx`/请求 **2.245 一格没动**，而它现在是这条腿剩下的最大一笔系统调用（小计
2.28 里有 2.245 是它）。它的构成是"主文件一次 + 每个候选孪生一次"：命中孪生的 URL
是 2 次，没孪生的是 3 次（两次注定失败的候选各一次 `lstat`）。要再往下压就得动
**负结果的粒度**（比如把"这个目录下没有 `.br`/`.gz`"并成一次判断），那是另一条刀。

### 4.14 h2 每批最多吐 64 KiB：`static-h2` 的 2.7 GiB 是从「批次大小」里来的（**第九套装置**）

#### 机制：一批有多大，由**对端通告的窗口**决定，不由本库决定

`uvcpp_h2_connection::flush()` 最早是「把 nghttp2 里所有就绪的帧一次榨干」，然后整块交给
`uvcpp_tcp_client::write()`。榨多少是 `nghttp2_session_mem_send2()` 说了算，而它的出站
字节量上限是**对端通告的窗口**：`h2load` 的 `-w`（流窗口）与 `-W`（连接窗口）默认都是
`30`，也就是 2^30−1 ≈ 1 GiB。

于是平台那一格（1024 连接 / `-m 32`）下，服务端会把一条连接上**所有**就绪的响应体攒成
一批推出去。一批 = 32 条流 × 约 16.5 KiB ≈ **500 KiB**，而它同时存在于三个地方：

1. `session_->drain(out_)` 攒出来的那一批明文（`out_.reserve` 出来的 `std::string`）；
2. `flush()` 里 `make_shared<std::string>` + `swap` 之后挂在 `pending` / `write_buf_`
   上的同一批，一直活到 `on_write_done()`；
3. `SSL_write` 把它拷进写 BIO 的 `BUF_MEM` —— 链路是
   `ssl3_write_bytes` → `tls_retry_write_records` → `BIO_write` → `mem_write` →
   `BUF_MEM_grow_clean` → `CRYPTO_clear_realloc`。

第 3 条是常驻的那一条：**`BUF_MEM_grow_clean` 只增不减**，一条连接历史上最大的一批
就是它此后一直占着的容量。1024 条连接 × 约 500 KiB × 2（明文 + 密文）就是量级。

#### 判据一：峰值时刻的活堆归因（抽样，只用于排序）

压测第 25 s（`h2load` 仍在跑）给服务端发 SIGTERM，预载的 `libjemdump.so` 在信号处理器里
调 `mallctl("prof.dump")` 再 `_exit(0)` —— 于是 dump 落在**峰值**上。采样率
`lg_prof_sample:19`（512 KiB），`addr2line` 按 `/proc/<pid>/maps` 的模块基址符号化。

改动前，活堆 **816.8 MiB**，排下来只有两条：

| 栈 | 字节 | 占比 |
|---|---|---|
| `BUF_MEM_grow_clean` ← `mem_write` ← `BIO_write` ← `SSL_write` | 470.0 MiB | 58% |
| `uvcpp_h2_connection::flush()` 里的那一批（`out_.reserve`） | 344.3 MiB | 42% |
| 其余全部（合计） | < 1 MiB | <1% |

**这不是泄漏。** 压测停下 5 s 之后再 dump 一次，活堆只剩约 18 MB —— 连接关完就没了。
RSS 不回落是分配器的保留页（glibc arena / jemalloc `MADV_FREE` 衰减），
按轮次看 RSS 单调上涨（1691.9 → 2801.1 → 3425.0 MiB）是**分配器高水位棘轮**，不是活对象。

旁证（窗口消融）：把 `h2load` 的窗口降到 `-w 16 -W 16`（64 KiB），同一形状的
VmHWM 从 2807.9 MiB 掉到 586.4 MiB，而 `-w 20 -W 20`（1 MiB）仍是 2908.3 MiB ——
自变量确实是「一批多大」，不是「请求多大」。

#### 判据二：修完之后的精确账（`mallctl`，无抽样误差）

改法只有一处：`uvcpp_h2_session::drain(std::string& out, size_t max_bytes = 0)` 多一个
上限，`uvcpp_h2_connection::flush()` 传 `k_max_drain_batch = 64 KiB`。断点**只判「攒够
没有」，不切帧**：`mem_send` 一次给一整帧，而「没榨完的留在 nghttp2 自己的出站队列里」
本来就是合法状态（下一次 `drain()` 接着吐）。所以一批最多超出上限**一帧**。

同一形状（c1024 / `-m 32`）、同一时刻（t=25 s）、同一条 30 s 压测，读分配器自己的账：

| 指标 | 改动前 | 本版 | 变化 |
|---|---|---|---|
| `Allocated`（活堆） | 1472.8 MiB | 382.0 MiB | **−74.1%** |
| `active` | 1551.0 MiB | 451.6 MiB | −70.9% |
| `metadata` | 30.9 MiB | 26.9 MiB | −13.0% |
| `resident` | 2206.4 MiB | 634.4 MiB | −71.3% |
| `mapped` | 2266.5 MiB | 698.4 MiB | −69.2% |
| `retained`（脏页） | 902.5 MiB | 319.6 MiB | −64.6% |
| `VmRSS`（同一刻） | 2054.9 MiB | 583.5 MiB | −71.6% |

另一套口径（只用内核的 `VmHWM`，不预载 jemalloc；每形状先跑一轮热机丢掉）：

| 形状 | 改动前 HWM | 本版 HWM | 改动前 rps | 本版 rps |
|---|---|---|---|---|
| A `static` c1024 `-m 32`（平台形状） | 2890.3 MiB | **724.1 MiB** | 63,366 | 71,158 |
| B `static` c1024 `-m 1` | 492.6 MiB | 436.1 MiB | 42,896 | 47,661 |
| C `static` c256 `-m 32` | 766.0 MiB | **215.6 MiB** | 63,584 | 69,029 |
| D 非静态 c1024 `-m 32`（地板） | 144.2 MiB | 145.1 MiB | 582,836 | 620,825 |

D 那一行是**对照臂**：它不经过静态处理器，两臂的 HWM 只差 0.6%，而 rps 也有 +6.5% ——
也就是说四个形状里普遍存在一个「后跑的那一臂更快」的机器漂移，rps 的涨幅不能全部记在
这一刀头上。**内存那条线不受影响**：A/C 掉的是 4 倍与 3.6 倍，D 一格没动。

#### 判据三：CPU 上不花钱（配对 A/B）

饱和档的 rps 量的是「谁先撞墙」，跨轮不可比；同一臂连着跑三遍，臂内极差就有 9%，
足以把改动的效果整个盖掉。所以改成**交替**起服务（改动前 / 本版 轮流，各 3 轮 × 3 次读数），
只看**同一轮里两臂的差**：

| 轮 | 改动前 µs/请求 | 本版 µs/请求 | Δ |
|---|---|---|---|
| 1 | 118.16 | 115.60 | −2.56 |
| 2 | 97.67 | 93.47 | −4.20 |
| 3 | 93.82 | 92.98 | −0.84 |

**配对差中位 −2.24 µs/请求**（口径：`/proc/<pid>/stat` 的 (utime+stime) ÷ 该轮 2xx 数）。
三对里本版全部更省 —— 封顶没有代价，方向上还略好（少一次大块 `memcpy` 与少一轮分配器
增长）。

#### 剩下的那一块，以及为什么不动它

封顶之后写 BIO 那一栈**仍然是剖析里最大的单条**（约占采样总量的 60%），只是绝对值掉了
一个数量级：现在每连接的发送缓冲封在 64 KiB，而残余的每连接约 373 KiB 里，大头是
**每连接固定缓冲**（TLS 16 KiB 读 + 16 KiB 写 + nghttp2 出站 buf，约 56 KiB/连接，
见剖析里 `tls_setup_read_buffer` / `tls_setup_write_buffer` / `nghttp2_bufs_init3`
三条各占约 4.5 MiB 缩放值）与分配器保留（`resident − allocated` = 252 MiB）。
不是某一次拷贝。

**没有**再做「写 BIO 排空后换一个 `BIO_s_mem()`」：那最多省 64 KiB × 1024 ≈ 64 MiB
（HWM 的 ≤9%），代价是给 TLS 写路径加一条新的失败模式。按「只动占比最大的那块」的
口径，这块已经被上一刀吃掉了。

#### 一句关于这把尺子的话

jemalloc 采样剖析的**绝对量不能当尺子**：同一份 dump 按它自己存的缩放值求和，
比同一时刻的 `Allocated` 低 3.5×（`lg_prof_sample:16`）到 9.7×（`:19`），而两个
采样率之间又彼此对不上。所以本页一律**用剖析看排序、用 `mallctl` 看总量**；
两张表不要混读。

### 4.15 静态整读的名额是在哪根线程上还的：`static-h2` 那批假 503（**第十套装置**，仓内确定性用例 + 交替 A/B）

#### 机制：名额的持有时长被「循环线程有多忙」决定了

工作池闸门（`uvcpp_web_work_limit`，见 `src/webapp/uvcpp_web_work_limit.h`）封的是
「**并发的磁盘读**」。可是 `1.6.42-dev` 之前，静态整读那条路是这么记账的：

    loop 线程      acquire_slot() 之前先投池
    worker 线程    read_job()：取名额 → 读盘
    loop 线程      after_work()：还名额

**还名额那一步跑在循环线程上，而循环线程正是高负载下最忙的那一根。** 于是名额的持有
时长不是「读盘要多久」，而是「读盘要多久 **+ 从读完到循环线程轮到 `after_work`**」。
压满的时候后一项远大于前者：`in_flight` 顶到上限（`UV_THREADPOOL_SIZE=64` 时是
`64 × 4 = 256`），真正在读盘的只有 ≤ 64 个，后来者一律被 `503 + Retry-After` 回绝。

这不是新病理，是**同一个病理的第二条路**：分片那条路 2026-09-24 已经改成「按块借还」
（`1.3.6-dev`，见 `uvcpp_web_file_transfer::set_chunk_gate()`），当时服务端日志的现场
是 `工作池已满（在途 0 / 16）` —— **在途 0 却拒绝**。整读这条路的现场是
`工作池已满（在途 256 / 256）`，两行日志说的是同一件事：**账面上的"在途"与实际并行
度脱钩了**。

#### 修法：记账搬到 worker，派发留在 loop 线程

「在 worker 上直接 `release()`」是**不安全**的：唤醒回调必须跑在**注册它的那根线程**
上，而现有两个注册方（`src/webapp/uvcpp_web_file.cpp` 的分片块闸门 → `resume()`、
`src/webapp/uvcpp_web_upload.cpp` → `on_slot_available()`）回调里都要续做 loop 上的
I/O —— 从 worker 里同步派发等于让它们跑在 worker 上，那是数据竞争。

所以把闸门的「记账」与「派发」拆开：

| 入口 | 记账 | 派发 | 在哪根线程上调 |
|---|---|---|---|
| `release()` | 当场 | 当场 | 唤醒回调所属的那根（= 注册它的那根） |
| `release_deferred()` | 当场 | **不派发** | 任何线程（worker 就是这一支） |
| `dispatch_wakeups()` | —— | 派发 | 只在唤醒回调所属的那根 |

`run_job()` 在 worker 上读完**当场** `release_deferred()`，同一笔任务在 loop 线程上的
`after_work` 补那一刀 `dispatch_wakeups()`。语义上有一处要紧的地方：**不会丢唤醒** ——
等待者只在「在途数已达上限」时才注册，那一刻必然至少有一个在途任务还没还过名额，它
结算时的检查必在注册之后 ⇒ 一定看得见这个等待者。

#### 判据一（确定性，不吃压测噪声）：仓内两组用例，且**变异必须变红**

`tests/functional/web_app_worklimit_func.cpp` 新增两组：

- `release_deferred_split` 钉闸门自身：账要**当场**记上；`release_deferred()` 的栈上
  **不许**发生派发；满员时两种还法都不许叫（无效唤醒风暴）。
- `worker_release_flushed_by_after_work` 钉**接线**（`uvcpp_web_static` 到底有没有照
  这套契约用）：上限压到 1，测试线程占住那唯一的名额，让一条**分片**请求停在块边界上
  并登记唤醒（`wakeup_count() == 1`，有界轮询，这是前提断言）；然后测试线程故意
  **只** `release_deferred()` 不补派；再让一个**冷文件**的整读请求去打整读挂载点 ——
  它 worker 里那次 `release_deferred()` 与 `after_work` 里那一刀是**唯一**还能叫醒那条
  分片传输的东西（它自己一个名额都没占、池子里也没有别的活儿）。

**变异实测**：把 `after_work` 里那两行删掉 ⇒ 该组 2 条红
（`整读那次 after_work 的补派必须叫醒挂住的分片请求`、`被唤醒之后那条一次性条目应当
已被消费掉`）。这一条比红本身更重要：**在这个组存在之前，"接线漏了补派"没有任何用例
盖得住**，而它的症状不是慢一点，是那条响应**再也不来**。

#### 这把尺子上的一处坑（如实记）

第一版用例把红绿判在「A 的 `send_wait(req, resp, 8000)` 超时返回非 0」上。实测
**那个超时不生效**：`uvcpp_http_client.h` 写明它靠 Windows 的
`SO_RCVTIMEO`/`SO_SNDTIMEO` 实现、POSIX 上「传入的值会被忽略」，单独验过一遍 ——
`send_wait(req, resp, 1500)` 对着一个从不回包的 socket 卡了 20 s 以上。于是变异下用例
是**挂住**（要等 ctest 的超时才发现、现场什么都不说），不是变红。改成：判定用有界轮询
（`a_replied`），A 那条线程等 `app.stop()` 关掉连接之后自然返回，那时才 `join()`。

#### 判据二：交替 A/B（**只认同一轮里两臂的差**）

形状同 §4.14 那一格（1024 连接 × `-m 32`、20 个静态 URI、`br;q=1, gzip;q=0.8`、
`UV_THREADPOOL_SIZE=64`、ext4 语料），但**只跑 20 s 且交替起服务**：改动前 / 本版
轮流、各 3 轮，读的是 `h2load` 自己那行状态码计数。

| 轮 | 改动前 5xx | 本版 5xx | 改动前 2xx | 本版 2xx |
|---|---|---|---|---|
| 1 | 17,883 | 0 | 1,663,894 | 1,643,319 |
| 2 | 14,747 | 0 | 1,648,941 | 1,638,128 |
| 3 | 15,126 | 0 | 1,635,661 | 1,658,477 |

5xx 那一栏的方向是**干净的**（≈2xx 的 **0.94%** → 0）；2xx 那一栏在噪声内，**不要**
拿它说事 —— 先单跑一轮看到 −2.5% 就当成劣化，交替三轮才知道那是漂移（第 3 轮反而是
本版多）。0.94% 听着不大，但它是同一台服务在同一形状下的**稳定拒绝**，不是抖动；
这一刀同时让名额早一拍变松（后来者不必再等那根最忙的线程）。

### 4.16 第三个编码器（`br`）：它换的是线上字节，而"换得值不值"取决于有没有 `cache_tag`（**第十一套装置**，仓内微基准 + 自建服务的交替 A/B）

这一节记的是 `1.6.48-dev` 那条可选开关 `UVCPP_ENABLE_BROTLI`（**默认关**）。
放在这一页是为了把口径钉死：**它不是一条提速改动**，判据是"① 线上字节更少、
② 解压回来逐字节相同"，而它到底值不值，要拿平台 `json-comp` 的计价公式算。

#### 机制：两条编码走的是同一条命中路径，编码名只在键里

`uvcpp_http_server::apply_compression_for()` 的变体缓存键是
`编码字符 + 档位字符 + cache_tag`（`src/web/uvcpp_http_server.cpp:2119-2122`）。
命中时只做一次 `std::map` 查找 + 一次 `shared_ptr` 递句柄 —— **gzip 与 `br` 是
同一条路径**。所以"开 `br`"在此处的代价是**每个 tag 一次**，不是每请求一次；
反过来说，响应没有 `cache_tag` 时它每请求重压，而 `br` 的编码比 deflate 贵得多。

#### 读数一：线上字节（三份真实语料，同一份 `libuvcpp_a.a`）

语料是平台 `json-comp` 那条 round-robin 的三个真实响应体，与条目
`build_json()` 的产物逐字节相同：

| 形状 | 原文 | gzip L6 | deflate L6 | **br q5** | br q0（缺陷档） |
|---|---:|---:|---:|---:|---:|
| `/json/25?m=4` | 4 190 B | 961 B | 949 B | **847 B**（−11.9 %） | 1 202 B（+25.1 %） |
| `/json/40?m=8` | 6 707 B | 1 313 B | 1 301 B | **1 168 B**（−11.0 %） | 1 685 B（+28.3 %） |
| `/json/50?m=6` | 8 397 B | 1 546 B | 1 534 B | **1 370 B**（−11.4 %） | 2 007 B（+29.8 %） |

百分比相对 gzip L6。q0 那一列是**缺陷**不是选项：服务器把 `compress_level()`
（默认 `-1`）原样喂给四参数那份 `compress()`，而 `clamp_brotli_quality(-1)` 当时
收成的是 `k_brotli_quality_min` = 0（"最快档"）而不是默认档 5 —— 也就是说"开 `br`"
会真的把响应**压大** 25~30 %。修法是一行哨兵（负数 = 该 method 自己的默认档），
用例里用一段**不对称**断言钉住：默认档那份必须与显式 q5 逐字节相同，**且 q0 必须
严格更大**。

#### 读数二：每请求代价，以及 `cache_tag` 开关把它乘到哪儿去

微基准（`-O2`、预热 20 次后取 4 000 次平均、`taskset -c 2`，同一进程内交替压
同一份 `8 397 B`）：gzip L6 **39.9 µs**、`br` q5 **144.7 µs**（**3.6×**，
`/json/40` 那份是 30.0 → 121.8）。

自建服务的交替 A/B（`uvcpp_web_app` 起在 ext4 语料上、64 条 h1 连接、
每臂 5 轮 × 200 000 次、`taskset -c 0-3`、三个 round-robin URI 轮转，
服务端是**同一份二进制**，只差客户端报不报 `br` 与 `/json` 填不填 `cache_tag`）：

| `/json` 填 `cache_tag` | `Accept-Encoding` | µs/请求（5 轮中位） | 线上字节/请求 |
|---|---|---:|---:|
| 是 | `gzip` | 8.85 | 1 498.9 B |
| 是 | `gzip, br` | **8.55** | **1 350.9 B**（×0.901） |
| 否 | `gzip` | 51.60 | 1 498.9 B |
| 否 | `gzip, br` | **88.60**（×1.72） | 1 350.9 B（×0.901） |

两件事一起读：

- **填了 `cache_tag`**：`br` 与 gzip 的差（8.55 vs 8.85 µs）落在轮次之间的散布里 ——
  命中路径上它不比 gzip 贵，而字节少 9.9 %。按平台
  `eff = rps × (min_bpr / bpr)²` 算，字节那一项是 **×1.23**。
- **没填 `cache_tag`**（也就是**今天条目的形状**：`handle_json()` 不填）：3.6× 的
  编码代价直接落到 rps 上，`eff` 变成 `0.58 × 1.23` = **0.72**，**倒扣 28 %**。

所以这一条不默认开、而且**库侧只落一半**：`br` 是库的能力，要不要在某个条目上开
属于那个条目的判断，前提是它先把响应体的指纹写进 `cache_tag`。

```bash
# （64 条 h1 连接、每臂 20 万次、三个 round-robin URI 轮转；
#   服务端用 CACHE_TAG=0|1 选填不填 cache_tag）
taskset -c 0-3 /tmp/brq/rig/run3.sh    # 逐臂读 /proc/<pid>/stat 的 utime+stime ÷ 2xx
```

字节/µs 那两张表的量具在仓外（`/tmp/brq/meas/m.cpp` 微基准、
`/tmp/brq/rig/run3.sh` 交替 A/B 与读 `/proc/<pid>/stat` 的 `cpr.sh`），
**不随仓库发布**；这一节记的是读数与口径。


## 5. 结果三：稳定性

10 分钟持续压测（动态路由 + 连接 churn + WebSocket 混合）：

| 项 | 读数 |
|---|---|
| 总请求 | **38 404 681，0 错误** |
| RPS | 64 008 |
| 延迟 | p50 **1 ms** / p90 1 ms / p99 **2 ms** / max **14 ms** |
| RSS 漂移 | **0.2%**（90.3 → 90.5 MB） |
| 句柄 | 252 → 254 |
| 连接 churn | 9 810 次建连 / **0 失败** |
| WebSocket | **7 804 条会话、23 412 帧 / 0 失败**，回收计数与建连数完全对上 |

另外单独做了**分段归因**（每段只做一件事，各自算 RSS 斜率）：只发内存型请求
（每请求新建连接）**−0.01 MB/min**、只建连/断开（3 757 次）**+0.01 MB/min**、只做
WebSocket 建连/回显/断开（2 733 轮）**+0.07 MB/min**、完全不发请求 **0.00 MB/min**。
四段全平 ⇒ 没有随时间累积的增长，长跑那条 0.2% 是分配器膨胀后收敛，不是斜坡。

> 这份归因第一次跑出来是 `19.52 MB/min` 的"持续增长"。真因不在被测对象：采样是按
> **进程名**取第一条匹配，而当时机器上还跑着另外两台同名的被测进程，样本里不存 pid ⇒
> 采样在进程之间跳了。证据是那条序列呈**单次 34 MB 台阶后永久平**（跳变，不是斜坡），
> 换成**按 pid 锚定**的采样后全程 9.47 MB 不动。写在这里是因为这类装置缺陷会让读数
> 骗人，而它长得和真泄漏一模一样。

## 6. 与 Hical 的对照

对照对象是 **[Hical61/Hical](https://github.com/Hical61/Hical)** —— 一个 C++20/26 的
Asio 框架，同样面向「百万空闲长连接」。它自己维护了一份性能报告（该仓库
`docs/performance_report.md`），其中 **§2.8「空闲长连接内存优化」** 给出的正是同一量：
**每条空闲连接的内存**。所以两边不用在两套口径之间换算，可以直接比。

Hical 自己在 §2.8 里给的账（v2.6.4 → v2.6.5）：

| 优化项 | 优化前 | 优化后 | 每连接节省 |
|---|---|---|---|
| `readBuf` 借还 | 连接常驻 8 KB `std::string` | `ReadBufferPool` 按需借还，空闲时不持有 | ~7.5 KB |
| `inputBuffer_` 懒分配 | 连接建立即分配 `PmrBuffer`（~2 KB） | `std::optional<PmrBuffer>`，第一次读才创建 | ~2 KB |
| **合计** | **~17.44 KB** | **~8 KB**（省约 55%） | |

同表给出百万连接量级：**~16.6 GB → ~7–8 GB**。
§2.9（v2.6.6）又加了一档：空闲连接 **+256 B**（协程帧栈），换来 `epoll_ctl` 调用数降 71.8%。

| 实现 | 每空闲连接 | 百万连接 |
|---|---|---|
| Hical v2.6.4（优化前） | ~17.44 KB | ~16.6 GB |
| Hical v2.6.5 / v2.6.6 | ~8 KB（v2.6.6 再 +256 B） | ~7–8 GB |
| **libuvcpp 1.1.33** | **4.62 KiB**（4 734 B） | **4.42 GiB** |

> Hical 那两格沿用**它的原文标法**（`KB` / `GB`）；它实际是二进单位，见下面第一条。

- 对本库 vs Hical **优化前**：**轻约 3.8×**（每连接少约 12.8 KiB）。
- 对本库 vs Hical **优化后**：**轻约 1.7×**（4.62 KiB vs ~8 KiB）。

**⚠ 这个 1.7× 有一处口径不确定，写清楚免得被读成强结论。** Hical 在那句话里同时注明
「内核侧 TCP 缓冲 ~4 KB/连接不可优化」。**本文的 4.62 KiB 是进程 RSS 增量，只含用户态**；
如果 Hical 的 ~8 KB 里已经含了那 ~4 KB 内核缓冲，那么同一口径下它剩下的用户态部分约
4 KB，两者**接近持平** —— 差别是本库的机制里压根没有常驻读缓冲，而它需要一套
`ReadBufferPool` 借还来达到同一格。该文档没有把这个口径写明，所以两种读法都列在这里，
不单选对本库有利的那个。**优化前那一格（17.44 KB）没有这个歧义。**

**其余可比性说明**：

- 两边都是**外推**（都撞端口/内核墙），所以都是"斜率可信、截距不可跨机器比"。截距差异
  明显（本机 9.95 MB，因为这台还带着静态缓存、会话表与已初始化的协议层）。**斜率才是
  可比的量**，上表据此下结论。
- **单位口径其实同一个**（这里先前写成"不同"，是我没查）：Hical 标的是 `KB` / `GB`，但它
  那几个数**只在二进读法下自洽** —— `17.44 × 1024 × 10⁶ B = 16.63 GiB`，正好对上它写的
  **~16.6 GB**；按十进读成 `17.44 KB` 算出来是 `16.24`，对不上。所以它的 `KB` 是 KiB、
  `GB` 是 GiB，与本文同口径，**上面那两个倍数不用折算**。
- **平台不同**：Hical 的数据出自它自己文档所述环境（Linux VM），本文是 Windows / MSVC
  / 环回。跨平台比较请带上这一条。

## 7. 这一页不是什么

- **不是跨平台的定论**，也不是跨项目的绝对排名 —— 见第 6 节最后三条。
- **不是单核之外的成绩**。上面所有吞吐都是**一个事件循环线程**（静态那几条走工作池）。
  要横向扩就起 N 个进程。别把 75 k 当成"每核 75 k 且不可再扩"。
- **不是 TLS 读数**。TLS 的稳态代价另有一组（约 −23% ~ −30% RPS，256 KB 响应受 AES-GCM
  单核吞吐限制降到 119 MB/s）；那一组的基线对照**归因未闭合**，所以没有放进这一页。

## 8. 复现方法

测量装置是一组独立脚本（Node + Python，跑在靶场进程之外），不随库发布。方法本身足够
简单，按下面三步就能复刻：

1. **建连**：分档建立 N 条 TCP 连接（N = 0 / 8k / 16k / 24k / 32k / 40k / 48k / 55 000），
   每条建好后发一个请求并读回响应 —— **逐条复检**，失败的连接不计入 N 且要单独报数。
2. **采样**：每档稳定后读被测进程的 RSS（Windows 是 `WorkingSet64`，Linux 读
   `/proc/<pid>/status` 的 `VmRSS`）。**按 pid 采样，不要按进程名** —— 见第 5 节那个坑。
3. **拟合**：对 (N, RSS) 做最小二乘，报**斜率、截距、R²、每点残差**。R² 不接近 1 就说明
   这条直线不成立，此时不要外推。

吞吐那一组用 `autocannon`（15 s/档，同机）；长跑那组是 10 分钟的自建压测循环，同时统计
错误、延迟分位、句柄数与 RSS 漂移。
