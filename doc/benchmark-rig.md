# 压测靶场

怎么在本机量出可信的 RPS 与 QUIC 大载荷吞吐，以及**为什么这件事比看上去难**。

这一页不是读数记录 —— 读数在 [`benchmark.md`](benchmark.md)。这里是**量具本身**：
怎么建、怎么跑、什么情况下读数不作数。

## 为什么要单独开一个靶场

`examples/webapp_demo` 看上去可以直接当靶场：它有个 `--serve` 模式，`/hello` 返回一份
内存里的 JSON，正是 `benchmark.md` 测的那类动态路由。但它**每个请求都写一行访问日志**，
而那一行要过全局日志锁（一次请求五次）、两次 `vsnprintf`，再 `fwrite` 到 stdout。

实测这个差别很大：同一台机器、同样的负载下，把访问日志关掉，**吞吐从 ~26 000 涨到
~34 500 RPS（+33%）**。拿 demo 当靶场，量到的主要是日志系统的价钱。

所以靶场 `bench/bench_server.cpp` 默认**一个中间件都不装**，把日志变成一根能单独扳动的
旋钮（`--access-log`），于是「日志值多少 RPS」本身也成了一个可以量出来的量。

## 建与跑

靶场默认**不建**，也不进 CI —— 它是量具，不是功能。

靶场建在 webapp 之上，所以**任何已经能建 webapp 的树**，加一个开关重新 configure 就能建它：

```bash
cmake -S . -B build-webapp -DUVCPP_BUILD_BENCH=ON
cmake --build build-webapp --config Release --target uvcpp_bench_server
```

（全新工作区也行，只是要先把 webapp 的依赖拉下来 —— llhttp 与 nlohmann/json 走
`FetchContent`，和建 webapp 是同一套。多配置生成器下 `--config Release` 不能省，
否则建出来是 Debug，读数就没有意义了。）

`UVCPP_BUILD_BENCH=ON` 配一个 `UVCPP_BUILD_WEBAPP=OFF` 的树不会报错，只是不建靶场
（靶场是 webapp 上的一个服务）。

Windows 上 `copy_test_dlls` 会把 `uvcpp.dll` / `uv.dll` / `llhttp.dll` 一并拷到靶场输出
目录 —— 少了这一步，靶场会以 `0xc0000135` 静默退出，而**静默退出的靶场在压测脚本眼里
和"服务起不来"是同一件事**，很容易被误读成服务端的锅。

跑起来：

```bash
uvcpp_bench_server --port 8080
```

启动横幅会把这份读数的**全部配置**打出来 —— 版本、端口、是否装访问日志、日志等级、
内存池开关、try_write 开关。这不是装饰：**一份不带配置的 RPS 不是结论，是传闻**。端口传
`0` 时由内核分配，实际端口只有横幅里有。

| 开关 | 作用 |
|---|---|
| `--port N` | 监听端口，`0`（默认）= 内核分配 |
| `--access-log` | 装上访问日志中间件（用来量它的价钱），默认不装 |
| `--log-level L` | `TRACE`/`DEBUG`/`INFO`/`WARN`/`ERR`/`FATAL`，默认 `WARN` |
| `--static <dir>` | 额外把静态根挂到 `/assets`，默认不挂 |
| `--loops N` | 事件循环数，`1..64`，默认 `1`。`N == 1` 与**不传这个开关逐字节相同**；`N > 1` 是「1 条接受者 + N−1 条工作循环」 |
| `--help` | 打用法就退，不启服务 |

路由有三条：`GET /json`（内存里预先拼好的 JSON）、`GET /text`、`GET /stats`。
`/stats` 打 `{"loops":n,"per_loop":[…],"total":N}` 的连接分布，**只在 curl 时被访问**，
不在 `/json` 热路径上。它是多循环那条判据的取证口：

> **分布不是判据，能看见分布才是判据。** 只报「RPS 涨了」说明不了「涨是因为几条工作
> 循环都在干活」—— 「只有一个循环真干活」与完全成功的读数**逐字相同**。

## 驱动器：为什么是多个生成器进程

```bash
cd bench && npm install         # 依赖声明在 bench/package.json；本仓不 vendor 它
node bench/driver.js --url http://127.0.0.1:8080/json --proc uvcpp_bench_server \
     --nproc 4 --duration 15 --connections 25
```

`bench/package.json` 把 `autocannon` 钉在**精确** `8.0.0`（不写 `^`）：现有全部读数是
这个版本跑出来的，换版本就换了量具，旧数不能比。`package-lock.json` 一并入库
（钉传递依赖，对量具比对应用更要紧）。锁里的 `resolved` **一律指向 `registry.npmjs.org`**，
不带本机 npm 配置里的镜像 —— 否则等于把某一面镜像钉进仓库。装出来的 `node_modules/`
已在 `.gitignore` 里。

单个 `autocannon` 是单线程 JS，**它自己会先到顶**。本机实测：单进程时生成器吃满一个核、
服务端也吃满一个核，两边同时到顶 —— 这种读数是**没有分辨力**的，既说明不了服务端能跑多少，
也说明不了还能不能更快。所以驱动器铺 N 个生成器进程，把生成器这一侧的算力摊到多个核上。

### 判据是「服务端占了几个核」，不是 RPS

驱动器每次都会报服务端占了多少个核，并且**按它判结论**：

| 服务端占用 | 含义 |
|---|---|
| ≥ 0.9 × **工作循环数** | 服务端到顶 —— 这个 RPS **是服务端的能力** |
| < 0.9 × **工作循环数** | 服务端没到顶 —— 这个数只是**生成器的上限**，不能当服务端性能 |

**门槛是「工作循环数」，不是 `--loops N`。** 这两者差一，而且差得很要命：`--loops N`
是「1 条接受者 + N−1 条工作循环」，而 **0 号那条接受者不承载任何连接**（只看它转发，
`/stats` 里 `per_loop[0]` 恒为 `0`）。所以 `--loops 4` 的服务端最多只能占 **~3 个核** ——
拿 `0.9 × 4 = 3.6` 去判，**永远**判「没到顶」，把真实能力印成「没量到」。`N == 1` 时
没有接受者/工作之分，那条循环自己干全部活，门槛就是 `0.9`。

驱动器（`bench/driver.js --loops N`）按这个规则给门槛。`--loops N` 的**绝对值**同样只在
同一台机器上可比，理由与上面那条一样。

量不到服务端 CPU 时驱动器退出 `3`（**没判**），而不是当成 0 报绿。退出码沿用本仓的
三值约定：`0` 判过 / `3` 前提不满足。

这一条是整页最要紧的规矩。少了它，"RPS 涨了"和"这次生成器恰好更闲"长得一模一样。

## 本机不是一台安静的压测机

量之前先看清机器。本机（2026-09-21）是 **Intel Core Ultra 5 125H，14 核 / 18 线程，
移动端 P+E 混合，3.6 GHz**，而且是一台**有人用的工作站**：基线负载 ~40%、559 个进程、
远程桌面与浏览器常驻。

这有两个后果。

**一、P 核与 E 核差很多。** 服务端线程落在哪一类核上，读数能差一倍。所以量之前**把服务端
钉在一个核上**，别让它中途迁移：

```powershell
$p = Get-Process uvcpp_bench_server
$p.ProcessorAffinity = 1        # 逻辑 CPU 0，在本机是 P 核
$p.PriorityClass = 'High'
```

不钉核时同一个配置连跑两轮能差 **104%**；钉核后落到 ~9%。**9% 也只是能用，不是很好** ——
所以下面说的"相对测量"要按多轮最小值判，不要按单轮。

**`--loops N>1` 时钉的不是一个核，是一个核集**，而且有一条容易踩空的规矩：**每个物理 P 核
只给一个逻辑 CPU**。本机的 P 核 HT 对是 `{0,1} {10,11} {12,13} {14,15}` —— 把 8 个逻辑
核全给出去，HT 兄弟会**被算成两个核**，占核数虚高，那个比值就没意义了：

```powershell
$p = Get-Process uvcpp_bench_server
$p.ProcessorAffinity = 0x5401   # {0,10,12,14}：4 个不同物理 P 核，每核一个逻辑 CPU
$p.PriorityClass = 'High'
# 回读！不读回 = 静默失败（本仓撞过：五档数字照打、一次都没绑上）
'{0:x}' -f [int64]$p.ProcessorAffinity
```

掩码要和臂一起换：单循环臂给 `0x1`，`--loops 4` 给 `0x5401`。生成器一律避开**全部 8 个
P 逻辑核**（兄弟线程偷的是同一份执行资源），本机给 `{2..9,16,17}`。读数对不上就先怀疑钉核，
**钉核回读不符要退 3，不能当一次测量记下来**。

`--loops N>1` 还有一个只有真跑过才知道的前提：**这台机器推不动 4 条循环的服务端到顶**。
两种驱动方式各撞一头，**形状**是稳的（下面是同一时段的扫描，只用来看方向，**不是读数**）：

| 驱动方式 | 谁先到顶 |
|---|---|
| 流水线 `1`、10 连接 | **回环路径**：服务端只到 ~3.2 核、生成器 ~79%，两边都不满 |
| 流水线 `4~16` | **生成器**：99%，服务端掉到 ~170% |
| 连接数 `10 → 25 → 50` | 反而**更慢**（与上面第 3 条同源：每次读事件的固定开销随连接数放大） |

所以多循环的**绝对值**在本机目前拿不到 —— 这不是库的问题，是**装置**的两头都够不着。
要拿到得换一台更闲的机器，或把生成器摊到更多物理核上（本机生成器只有 10 个 E/LP-E 核；
把 P 核让给生成器就得先减服务端的循环数，那是另一套臂）。

**二、绝对值只在同一台机器上可比。** `benchmark.md` 那条 **75 791 RPS** 是在另一台机器
（Windows 10 1903）上量的；本机同口径只有 **~35 000**。这不是回归，是硬件不同 ——
**两台的数不能相减，也不能相除。**

## 已经量出来的三件事

单事件循环、`GET /json`、Release、内存池 ON、try_write ON：

| 靶场 | 访问日志 | 生成器 | RPS | 服务端占核 |
|---|---|---|---|---|
| `webapp_demo /hello` | **ON** | 1 × 10 | ~26 000 | — |
| `webapp_demo /hello` | **ON** | 4 × 25 | 19 827 | 0.94 |
| `bench /json` | off | 1 × 10 | **34 483** | 0.93 |
| `bench /json` | off | 4 × 25 | 26 106 | 0.95 |

1. **服务端在每一种配置下都钉在 ~0.94 核** ⇒ 瓶颈在服务端，不在生成器（4 个生成器时
   每个只占 ~42%）。
2. **访问日志值约 25% 的吞吐**（26 000 → 34 483）。它每请求过多次全局锁加两次
   `vsnprintf`，中间件在 `src/webapp/uvcpp_web_middleware.cpp:92`。
3. **连接越多越慢**：10 连接 34 483 → 100 连接 26 106，**服务端 CPU 基本没变**。
   同样的 CPU 干更少的活 ⇒ 存在一个**每次读事件的固定开销**，且它随连接数放大。
   头号嫌疑是接收缓冲：每次读都按 64 KiB 分配，而分配函数**整块清零** ——
   `uvcpp_alloc_arry` 是 `malloc` 紧跟一次 `memset`，见
   `src/uvcpp/uvcpp_alloc.h:102-105`。一次读事件白写 64 KiB，这笔钱与收到多少字节无关。

第 3 条还没有定论（**上表是四次独立运行，不是同一轮的对照**），要坐实它得先把
「按读事件计价」和「按请求计价」分开量。在那之前，它是**嫌疑**，不是结论。

## QUIC 吞吐量具（`bench/bench_quic.cpp`）

上面那一套量的是 HTTP/1.1 的 RPS。QUIC 是另一条路（跑在 UDP 上、由 ngtcp2 驱动），
上面的靶场够不着它，于是「大载荷吞吐」这个数只能从库外引一份靶场。那个缺口本身就是
个洞：**「改一处到底有没有用」在本仓里无法回答**。这个量具补的就是这条能力。

它建在 net 层上，所以 **`UVCPP_BUILD_WEBAPP=OFF` 的树照样建得出来**（上面那一套建不出来）：

```bash
cmake -S . -B build-quic -DUVCPP_BUILD_NET=ON -DUVCPP_ENABLE_OPENSSL=ON \
      -DUVCPP_ENABLE_QUIC=ON -DUVCPP_BUILD_BENCH=ON
cmake --build build-quic --target uvcpp_bench_quic --parallel 2
```

三种模式：

| 模式 | 量什么 |
|---|---|
| `--mode=push` | **纯发送方向**：客户端 `write_stream(N)` 带 FIN，服务端只收不回 |
| `--mode=echo` | **往返**：服务端把收到的原样回写（issue #34 那张表就是这个形状） |
| `--mode=udpfloor` | **地板**：裸 `uv_udp` 对打同尺寸报文 —— 它不是本库的读数。`--pkt=N` 定每个数据报装多少字节，**必须与 QUIC 那一档实际用的数据报一样大**，否则两条读数不可比：地板也是按包数付内核税的 |

两条口径是**量具的一部分**，不是随手选的：

- **每个尺寸换一条新连接。** 拥塞窗口是连接级的：同一条连接上先跑 2 MB 再跑 8 KB，
  第二笔量到的是被第一笔养肥的 cwnd，而不是「8 KB 该有多快」。
- **丢掉第一轮。** 冷启动那轮会把握手尾巴与初始窗口一起量进去，不是稳态吞吐。

### 本机实测（2026-10-09，Windows 11，MinGW64，`--rounds=15`，每档 15 轮取最小值）

六档一次跑完，push / echo / 地板三张表**同一次运行**。跨次运行会漂（这台机器上同一份
二进制、同一个尺寸，换个 session 复量能差 ~6%，见下面 ⚠️），所以引用这些数时连
**是哪一次运行**一起说。

**下面这一版是 `ack_thresh = 16` 之后的那一次**（理由、代价与交错 A/B 见
`src/quic/uvcpp_quic_session.cpp` 里 `kAckThreshold` 那段注释）。原始输出：
`_probe/quicack/rig_after_ack16.log`。

| 尺寸 | push 最小 | push cyc/B | echo 最小 | echo cyc/B | 裸 UDP 地板（`--pkt=1444`） |
|---|---|---|---|---|---|
| 1 KiB | 0.016 ms | 46.80 | 0.025 ms | 72.24 | 0.013 ms（74.6 MB/s） |
| 8 KiB | 0.052 ms | 18.90 | 0.100 ms | 36.60 | 0.051 ms |
| 64 KiB | 0.400 ms | 18.27 | 0.769 ms | 35.16 | 0.438 ms |
| 256 KiB | 1.585 ms | 18.07 | 3.158 ms | 35.88 | 1.758 ms |
| 1 MiB | 6.611 ms（151.3 MB/s） | 18.72 | 13.472 ms（74.2 MB/s） | 37.86 | 7.176 ms（139.4 MB/s） |
| 2 MiB | **13.916 ms**（143.7 MB/s） | 19.62 | **27.245 ms**（73.4 MB/s） | 38.44 | **14.569 ms**（137.3 MB/s） |

⚠️ **这一版读数取自"数据报上限放开之后"**（见下面 PMTUD 那一节）。地板那一列
也因此换了口径 —— 上限还钉在 1200 时记的 17.759 ms 是 `--pkt=1200` 量的，而 QUIC
现在发到 1444，拿旧地板当分母会**高估**库的开销（上一轮里、同一台机器同一次运行，
`--pkt=1200` 的 2 MiB 地板是 17.096 ms，`--pkt=1444` 是 14.390 ms）。**地板自己会动**
这一点正是那个缺陷的量：地板也按包数付内核税。

读法：**push 那一列已经贴着地板了**（2 MiB：13.916 对 14.569 ms）—— 单向大载荷上，
本库的 QUIC 栈相对裸 UDP **没有可测的开销**。往返那一列是地板的 **1.87 倍**，多出来
的那一倍是反向的 ACK/流控反馈，地板没有对端要回话。而地板那 14.569 ms 里全是本机
UDP 回环的税（10.0 µs/包），本库一个字节都没摊上。绝对数只在同一台机器、同一次运行
内可比。

**小尺寸那几行说明这个量具量的是什么**：push 的 cyc/B 在 1 KiB 是 46.80、8 KiB 是
18.90、2 MiB 是 19.62 —— **非单调**，因为小尺寸那端单笔只有 0.016～0.052 ms，几乎
全是建流尾巴与首次发送的固定开销，`cyc/B` 在那一点上不是吞吐指标。要比"库快不快"
看 1 MiB / 2 MiB 两行。

**对照：`ack_thresh` = ngtcp2 默认的 2（改动前的那一轮）**

| 尺寸 | push 最小 | push cyc/B | echo 最小 | echo cyc/B | 裸 UDP 地板（`--pkt=1444`） |
|---|---|---|---|---|---|
| 1 KiB | 0.014 ms | 40.36 | 0.022 ms | 64.64 | 0.012 ms（78.8 MB/s） |
| 8 KiB | 0.062 ms | 22.81 | 0.135 ms | 49.25 | 0.051 ms |
| 64 KiB | 0.538 ms | 24.18 | 1.170 ms | 53.09 | 0.438 ms |
| 256 KiB | 2.320 ms | 26.46 | 4.409 ms | 50.11 | 1.760 ms |
| 1 MiB | 9.691 ms（103.2 MB/s） | 27.44 | 17.775 ms（56.3 MB/s） | 50.05 | 7.072 ms（141.4 MB/s） |
| 2 MiB | 19.364 ms（103.3 MB/s） | 27.58 | 35.575 ms（56.2 MB/s） | 50.40 | 14.390 ms（139.0 MB/s） |

⚠️ 这两轮是**不同的 session**，而本节开头那句"跨次运行能差 ~6%"正是针对这种比法 ——
所以别把下表之间的小差别当成信号。严格的前后对照是同一 session 里**交错**跑的两个
二进制（`_probe/quicack/ab.sh`），那一组给的 2 MiB push 是 1.37×。

两轮的**地板几乎没动**（14.390 → 14.569，落在漂移里），差的全在 push / echo 两列：
2 MiB push 19.364 → 13.916 ms（**−28%**，cyc/B 27.58 → 19.62），2 MiB echo
35.575 → 27.245 ms（**−23%**）。`cyc/B` 同向掉了近三成，说明省下来的是**本线程真少
干的活**（每包少一次 `sendto`），不是墙钟运气。

### 分块大小是量出来的，不是拍的

发送队列的分块大小（`uvcpp_quic_session.h` 的 `kChunkSize`）在三档上量过
（`--mode=push --rounds=9 --sizes=2097152`，同一台机器）：

| `kChunkSize` | 2 MiB 最小 | cyc/B |
|---|---|---|
| 16 KiB | 25.410 ms | 35.95 |
| **64 KiB** | **21.907 ms** | 30.68 |
| 256 KiB | 21.913 ms | 30.85 |

⚠️ 这张表量于**数据报上限放开之前**（那时 QUIC 被自己的常量钉在 1200 字节），所以
64 KiB 那行的 21.907 ms **不等于**上面**对照表**（`ack_thresh=2` 那一轮）里 2 MiB 那一档
的 19.364 ms —— 两处不可直接比，
它跟的是更早的那一版绝对值。放开之后**没有复量过**这三档，所以这张表只当"当初为什么
选 64 KiB"的记录读，别当今天的三档读数。

64 KiB 与 256 KiB 差 0.03%（噪声内），16 KiB 慢 16% —— 拐点在 64 KiB，往上加没有
回报，而一块的容量是**每条约活的流都要占的**，所以取小的那个。三档都由同一个脚本
改一个常量重编得来，原始输出在 `_probe/sweep.log`。

### 数据报大小：一条被自己的常量关死的 PMTUD

`uvcpp_quic_session.cpp` 里那个 `settings.max_tx_udp_payload_size` 原本逐字写着
`NGTCP2_MAX_UDP_PAYLOAD_SIZE`(1200) —— 也就是"任何路径都保证能过"的那个**下限**。
看着最保守，实际是**把 ngtcp2 自带的 PMTUD 整条关掉**：

- `conn_start_pmtud()` 拿 `min(对端 max_udp_payload_size, 本端 max_tx_udp_payload_size)`
  当硬上限；上限 =1200 时，ngtcp2 自带探测表 {1406, 1342, 1232, 1444} **四档全部越界**
  （`ngtcp2_pmtud.c` 里那个 `for` 循环把四档一路 `continue` 过去）；
- 于是 `ngtcp2_pmtud_finished()` 立刻为真 → `conn_stop_pmtud()`，此后每个数据报都被
  `conn_shape_udp_payload()` 钉死在 1200 字节。

症状就是包数：2 MiB 单向要 **1748** 个数据报，而本机每包约 10 µs 的内核税不打折。
改成 1500（典型以太网 MTU）之后 PMTUD 才真的会跑，路径上限停在探测表最大一档
**1444**（`ngtcp2_rtb.c` 只在**探测包**被确认时抬它）。

A/B：同一个 2 MiB，两组二进制**交错**跑，各 5 轮取最小值。

| | 数据报上限钉在 1200（对照臂） | 放开之后 |
|---|---|---|
| 接收侧 `on_read(DATA)` 次数 | 1743 / 1761 / 1766 / 1761 / 1747 | 1444 / 1407 / 1446 / 1442 / 1392 |
| push 最小 | 21.603 ms | **17.539 ms**（−18.8%） |
| echo 最小 | 39.866 ms | **35.459 ms**（−11.1%） |

第一行才是这个改动的**结构**证据：两组读数**一次都没有重叠**，而它不受墙钟噪声
影响 —— 这台机器上同一份二进制、同一个尺寸，最小值在 20.7～24.9 ms 之间跳，
**单看墙钟是分不出结论的**，交错 + 取最小值才分得出。cyc/B 同向：2 MiB 单向
33.51 → 25.25，往返 60.59 → 50.14。

全尺寸扫描（1024 B … 2 MiB，push/echo 各 3 轮交错）：**每一档都变快**
（+4.2% ～ +23.8%），没有一档变慢。

⚠️ 同一个常量还决定了**对外的 `max_udp_payload_size` 传输参数**，这次也一起从默认的
65527 收到 1500：我们宣布"收得下 65527 字节的数据报"，而两只端点的接收缓冲只有
4096 —— 以前撞不上，纯粹因为对端也是本库、也被同一个常量钉着；换一个照 RFC 走的
第三方实现就会在内核那层被截断。它进 Initial 包，是**线上一档行为**。

**两个入口各有一条 `static_assert` 守着**（同文件）：把上限钉回 1200、或把落点缓冲
缩到探测表最大一档(1444)以下 —— 编译就过不去。两种情况都会把 PMTUD **静默**关掉，
而静默正是它危险的地方（关掉之后一切照常工作，只是慢）。两条都用对照臂验过：
把常量改成 1200，两条断言同时报出各自的理由、构建失败；改回来即通过。

### 对照组：同一台机器上跑 MsQuic

上面这些读数一直**没有对照臂** —— 只能证明本库自己变快了。2026-10-09 补上：装置是
.NET 10 自带的 `System.Net.Quic`（即 MsQuic），在仓库外的 `_probe/quiccmp/`，口径与
本量具对齐（2 MiB 单向、15 轮取最小值）。

**先钉核再比。** 不钉核时 MsQuic 快约 1.7 倍，看着像"它在用更多核"；钉到同一个 P 核
（`start /affinity 1`）之后**差距基本不变**：

| 2 MiB push，钉 core 0（P 核） | min_ms | MB/s |
|---|---|---|
| uvcpp QUIC | 15.273 | 131.0 |
| **MsQuic QUIC** | **8.345** | 239.7 |
| .NET 自己的裸 UDP 地板 | 16.365 | 122.2 |

**核数解释不了它。** MsQuic 从 1 个逻辑核到 18 个几乎不缩放（不钉核 8.04 / 钉 P 核
8.345 / 钉 LP-E 核 11.071），而本量具本来就是单线程的 —— 所以「给 QUIC 加多循环」
**不是这笔账的解法**（多循环是"单核装不下时横向扩展"的账，不是"单核跑得慢"的账）。

**贵的是每一个数据报，不是每一个字节。** 同样 2 MiB、同样一个核，只把 .NET 裸 UDP
地板的**报文尺寸**换掉：

| pkt | 数据报数 | min_ms | MB/s |
|---|---|---|---|
| 1434 | 1462 | 16.365 | 122 |
| 8192 | 256 | 3.326 | 601 |
| 65507 | 32 | 0.930 | 2148 |

一个 QUIC 栈（8.345 ms）能比裸 UDP 灌包（16.365 ms）快一倍，只可能是它的**每个系统
调用搬的字节数**跟别人不一样。**在 Windows 上**本库是一个数据报一次 syscall（平台差异
见本节末尾的 ⚠️），数据报上限还被 ngtcp2 的 PMTUD 探测表钉在 1444（见上一节）。

**但"报文开大"不是 MsQuic 用的那一招。** 用 `netstat -s -p udp` 的累计值取差，数线上
真正走了多少个数据报：

| 2 MiB push | 线上数据报/轮（每方向） | min_ms | µs/包 |
|---|---|---|---|
| uvcpp QUIC | 1689 / 1691 | 13.586 | 8.04 |
| **MsQuic QUIC** | **1507 / 1508** | **6.838** | **4.54** |

**MsQuic 线上的数据报只少 11%**（≈1392 B/个，和本库的 1434 基本一样），时间却少一半
⇒ 不是"它的包更大"，是"它每个包更便宜"。

便宜在哪，还是用 .NET 裸 UDP 地板直接验（同一台机、同一个核、pkt=1434、`--uso=1`）：

| 地板这一档 | 线上数据报 | min_ms | µs/包 |
|---|---|---|---|
| 两个选项都不开（≈ 本库的处境） | 1462 | 16.365 | 11.19 |
| 开 `UDP_SEND_MSG_SIZE`(=2) | 1473 | **4.368** | 2.99 |
| 再开 `UDP_RECV_MAX_COALESCED_SIZE`(=3) | 1473 | 3.860 | 2.64 |

**线上数据报一个没少（1462 → 1473），时间少 3.7 倍** —— 省掉的只能是**系统调用**：一次
`SendTo` 交给协议栈 64 KiB，由它按 1434 字节切开送出去。这就是 Windows 的 **UDP 分段
卸载（USO）**，收方向对应的是**收合并**。MsQuic 的 4.54 µs/包正落在这个区间里，而本库
连它自己的裸 UDP 地板都在 11 µs/包那一档 ⇒ **「一个数据报一次 syscall」就是本库慢的
全部原因**，ngtcp2 那层没有可测开销。

⚠️ **代价与边界**：

① **上面那张 11.19 → 2.99 µs/包的表是 Windows 的数，别当成"libuv 的固有开销"。**
两个平台在这件事上差得很远，而且**分水岭在 libuv 里，不在本库里**：

- **Linux：libuv 已经自己做了这件事，一行代码都不用改。** `src/unix/udp.c` 的
  `uv__udp_sendmsg()` 一次从 `write_queue` 里取最多 **20** 个待发请求，折成**一次
  `sendmmsg()`**（`uv__udp_sendmsgv()` 里 `if (count > 1)` 那条分支；Linux/FreeBSD/
  Solaris 走 `sendmmsg`，macOS 走 `sendmsg_x`）。触发条件恰好就是本库 QUIC 的自然形状：
  写循环在一次同步调用里连发 K 个数据报 ⇒ **第 1 个**走单发 `sendmsg`，**后面 K−1 个**
  只进队列并起 `POLLOUT`，由回调按 20 个一批发出去。也就是说 Linux 上这条账**已经塌缩了
  约 20 倍**，不是 1。
- **Windows：libuv 里完全没有这条路。** `src/win/udp.c` 的 `uv__send()` 每个请求一次
  `WSASendTo`，`uv__udp_try_send2()` 就是个 `for` 循环；而 Windows 根本没有 `sendmmsg`
  这种"一次系统调用发 N 个数据报"的原语。

- ⚠️ **Linux 那半边是读码读出来的，本库没有在 Linux 上量过。** 直接判据是
  `strace -f -c -e trace=sendmmsg,sendmsg <bench>`：若 `sendmmsg` 次数 ≈ 数据报数/20，
  批量就真的生效了。**在跑出这张表之前，不要对外说"Linux 上没这个问题"。**

- 所以 Windows 上要拿到同样的效果**只有 USO 一条路**，而它必须绕开 `uv_udp_send`
  （`uv_fileno()` 拿句柄设 `UDP_SEND_MSG_SIZE` + 把 K 个数据报攒成一次发送）——
  那确实背离了"只用 libuv 的 I/O 原语"这个初衷。**要么不做，要么把这条能力做进 libuv
  自己**：Linux 那半边上游已经做了，Windows 这半边是上游的事，不是本库该私下绕过去的。

② 本库每轮比 MsQuic 多发 ~12% 的数据报（1690 对 1507）—— 那是控制包/ACK 策略的差，
是**另一笔**、且小得多的账。上面那张「报文开大」的表（1434→65507）则是**回环特有**的
便宜（回环 MTU 是 4294967295），真实 1500 MTU 的网上两边都只能发 ~1400 字节，
**别拿它外推**；USO 这一条不受它限制（真网卡支持就有效，不支持则设选项会失败）。

另注：`_probe/quiccmp` 里那两个常量原本写成 19 / 20，**两个都错**（正确值是 **2 / 3**，
见 `ws2ipdef.h`；20 其实是 `UDP_CHECKSUM_COVERAGE`）。在改对之前探针一直报"无效参数"，
于是"USO 在这台机器上装不上"被误当成了结论 —— 那是装置的错。改对之后全部档位都 OK。

### 尺寸从 2 MiB 拉到 128 MiB：差距不但不缩小，还满格

两个量具的默认尺寸表都封顶在 2 MiB（`bench_quic.cpp` 是 1 K/8 K/64 K/256 K/2 M），
所以「只测了 2 MiB，大文件未必输」是个**必须量掉**的问题。`--sizes=` 两边都收，
同一张表重跑（`--rounds=5`，丢第一轮）：

| 单流 push | uvcpp min_ms | uvcpp MB/s | MsQuic min_ms | MsQuic MB/s | 比 |
|---|---|---|---|---|---|
| 2 MiB | 14.895 | 134.3 | 8.804 | 227.2 | 1.69× |
| 8 MiB | 59.117 | 135.3 | 30.270 | 264.3 | 1.95× |
| 32 MiB | 230.093 | 139.1 | 119.347 | 268.1 | 1.93× |
| 128 MiB | 901.212 | 142.0 | 445.037 | 287.6 | **2.02×** |

两边都钉到核 0 再跑其中两档（对照臂不钉核时那个 2 MiB 的历史值也是这个量级）：

| 钉核 0 | uvcpp min_ms | MB/s | MsQuic min_ms | MB/s | 比 |
|---|---|---|---|---|---|
| 32 MiB | 238.848 | 134.0 | 107.188 | 298.5 | 2.23× |
| 128 MiB | 1000.126 | 128.0 | 424.209 | 301.7 | **2.36×** |

**两条独立的结论：**

1. **本库从 2 MiB 起就已经在稳态了。** 数据量翻 64 倍，吞吐只从 134.3 涨到 142.0 MB/s
   （+5.8%）；MsQuic 则到 8 MiB 才爬满（227.2 → 287.6，+27%）。所以「2 MiB 那组对本库
   不公、它还欠一个爬坡」这个假设**不成立** —— 那个 134 MB/s **就是它的稳态**，而
   MsQuic 在 2 MiB 上量到的反而是被爬坡压过的数。**拿 128 MiB 那一格去比才是公平的，
   而那一格是 2.02×（钉核 2.36×），比 2 MiB 那一格还难看。**
2. **每数据报成本在 64 倍量程上是个常数**，这是"机制就是那个机制"最硬的证据：
   - 本库：`recv_calls` 那一列 128 MiB 是 **92505** 次、每次 1452.4 B ⇒ 一次系统调用一个
     数据报；901.2 ms ÷ 92505 = **9.74 µs/次**（钉核 10.8）。
   - MsQuic：128 MiB ÷ ~1440 B ≈ 93200 个数据报；445.0 ms ÷ 93200 ≈ **4.78 µs/个**
     （钉核 4.55）。
   - 与 2 MiB 那一档量到的 **8.04 / 4.54 µs** 是同一个数。**常数 ⇒ 不是小尺寸的假象。**

**还没测的面**（要下更大结论得先补）：单笔超过 128 MiB。日志在 `_probe/quicsize/`（仓库外）。

### 并发流与双向：差距不会缩小，反而拉宽

两个量具原本都只支持**单流**。给两边都加了 `--streams=N`（`--sizes=` 仍写一个数，语义
变成**每条流**的字节数，所以一轮总量 = `streams × size`）。

**先做对照**（新开关必须在 N=1 时回到加它之前的形状，否则装置本身变了）。本库
`streams=1` 的 32 MiB 有三个独立读数：不传开关 **232.953 ms**、显式 `--streams=1`
**226.509 ms**、扫描里的第一档 **228.411 ms** —— 全部落在 226.5 ~ 233.0 ms，而改动前
那一档是 230.093 ms，就在这个区间里。`recv_calls` 分别是 23131 / 23115 / 23094
（**±0.16%**，比时间还紧 —— 数据报个数才是那个稳的量）。MsQuic 侧 108.3 ms
（改动前 119.3）—— 但**同一档的会话间漂移就有 9%**（这台机器不是安静的压测机），
所以下面的表**只比自己会话内的相对值**。

**固定总量 32 MiB、扫并发流数**（同一个会话里逐档交错：先 uvcpp，再 MsQuic）：

| streams | uvcpp min_ms | uvcpp MB/s | MsQuic min_ms | MsQuic MB/s | 比 |
|---|---|---|---|---|---|
| 1 | 225.7 | 141.8 | 101.9 | 314.0 | 2.21× |
| 2 | 230.2 | 139.0 | 93.7 | 341.7 | 2.46× |
| 4 | 236.0 | 135.6 | 89.9 | 356.1 | 2.63× |
| 8 | 236.2 | 135.5 | 92.3 | 346.7 | 2.56× |
| 16 | 237.6 | 134.7 | 89.5 | 357.4 | **2.65×** |

**并发流对两边的作用是反的**：本库 **−5%**（141.8 → 134.7 MB/s），MsQuic **+14%**
（314.0 → 357.4）。所以「我们可能只在单流上吃亏、并发起来就追上了」**是错的 —— 差距
从 2.2× 拉宽到 2.6× 并在那里停住。**

**两边的线上数据报在 1 流和 16 流下几乎一模一样**，这是"多流改不了这笔账"的直接证据：

- 本库：`recv_calls` 在 1/2/4/8/16 流下是 23105 / 23119 / 23089 / 23165 / 23132，
  `B/call` 恒定 ~1450 ⇒ **一次系统调用一个数据报，与流数无关**。
- MsQuic：`netstat -s -p udp` 增量，1 流每轮 23886 / 23894 个，16 流 24012 / 24020
  （**+0.5%**），而时间从 97.7 降到 89.9 ms ⇒ **数据报没少，只是每个便宜了 8%**
  （4.09 → 3.75 µs/个）。

**每数据报成本（32 MiB 档）：本库 9.8 ~ 10.3 µs，MsQuic 3.8 ~ 4.1 µs。** 这两个数各自
正好贴着自己那一侧的地板（不开 USO 是 11.19、开了是 2.99）⇒ 分水岭仍是"每个数据报几次
系统调用"，**多流改不了它，因为流的条数不改变数据报的个数**。

**echo（双向回写）**，同一个尺寸表、单流：

| 单流 echo | uvcpp min_ms | MB/s | MsQuic min_ms | MB/s | 比 |
|---|---|---|---|---|---|
| 2 MiB | 28.259 | 70.8 | 13.042 | 153.4 | 2.17× |
| 8 MiB | 111.076 | 72.0 | 46.648 | 171.5 | 2.38× |
| 32 MiB | 437.619 | 73.1 | 199.747 | 160.2 | 2.19× |

双向把两边的吞吐都砍掉约一半（本库 142 → 73 MB/s，MsQuic 288 → 160），而**比例几乎不动**
（push 2.0× → echo 2.2×）⇒ 每数据报那笔账在两个方向各付一次，比例守恒。

**仍未测**：`echo` × `--streams=N` 的组合。

### 这个量具是怎么被用上的：一次崩溃的根因

issue #34 报的是「大载荷下崩」。`--mode=echo --sizes=2097152` 20 次里崩 3 次
（`0xC0000005`），出错的那次读在 `ngtcp2_cpymem` ← `ngtcp2_pkt_encode_stream_frame`
里，目标区域是 `MEM_RESERVE` —— 也就是**读过了某个堆块已提交区的末尾**。

根因写在 `ngtcp2.h` 里：调用方必须把交给 `ngtcp2_conn_writev_stream()` 的那段数据
**原样留着**（"keep ... in tact"），直到 `acked_stream_data_offset` 说它被对端确认。
ngtcp2 存的是**指针**（重传帧链里 `ngtcp2_vec_copy` 只拷那个指针数组），所以任何
再分配都是 UB。当时那份实现在**两个方向**上都违反了它：

1. 缓冲区会**增长** —— `std::vector` 扩容把地址整个搬走；
2. 缓冲区会**前移** —— 丢掉已确认的前缀时把尾巴 `memmove` 上来，地址没变、字节变了。

先做的是对照：把「地址与字节都不许动」临时焊死（预留够 + 不做前移），
**20 次 0 崩**，而未修的对照是 **3/20**。正式修法是**分块发送队列** —— 每块出生时
`reserve(64 KiB)`、此后只写到这里为止，只在**整块**都被确认时才丢 —— 于是两条约束
都按构造成立，丢块 O(1) 且一个字节都不搬。

**「代价百分之几」这句话在这里量不出来，而且原因本身是个发现。** 把 HEAD 那份存储
换回来重编、跑同一个量具（3 次独立构建 × push/echo 各一次，`--rounds=15
--sizes=2097152`），**6/6 次都在 15 轮内报 `DATA MISMATCH`**：

| 第几次 | push 首个不符的流偏移 | echo 首个不符的流偏移 |
|---|---|---|
| 1 | 1 811 177 | 186 107 |
| 2 | 63 612 | 63 612 |
| 3 | 63 612 | 63 605 |

旧形状在那 6 次里**没有一次**吐出过完整的 2 MiB：量具连一行耗时都不打印，直接报
「第一个不符在流偏移 N」。所以它不是"比新版慢一点"，而是**交付的字节是错的**，
那个基线在 2 MiB 上根本不存在 —— 拿它当分母算百分比是没有意义的。崩（3/20）只是
这份实现最响的那种症状，**静默坏字节才是常态**。这也是为什么新用例
（`quic_stream_func.cpp` 第四阶段）宁可多花时间做**整条流的逐字节比对**：计数式判据
看这两种症状长得一模一样。

同一次调查还顺手拿掉了发送路径上每包一次的拷贝：两个端点现在先试
`uv_udp_try_send()`（同步，返回时 `data` 已死，不必拷），只有不是「已发出」才落回
原来那条异步拷贝入队的路。2 MB 一笔就是约 1700 次
`new char[]` + `memcpy` + `delete[]` 与约 1700 次多余的循环轮转。

## 这一页不是什么

- 不是读数记录 —— 读数属于跑它的那套硬件加配置，写在 [`benchmark.md`](benchmark.md)。
- 不是回归门禁 —— 靶场不进 CI，本机的噪声也不支持一个绝对阈值。
- 不是「本库比 X 快」的证据 —— 对照臂（MsQuic）只说明**差距落哪一类成本上**：每个
  数据报的系统调用，不是核数；而且那是**回环**上的数，别外推（见「对照组」那一节）。
