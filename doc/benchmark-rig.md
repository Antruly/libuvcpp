# 压测靶场

怎么在本机量出可信的 RPS，以及**为什么这件事比看上去难**。

这一页不是读数记录 —— 读数在 [`benchmark.md`](benchmark.md)。这里是**量具本身**：
怎么建、怎么跑、什么情况下读数不作数。

## 为什么要单独开一个靶场

`examples/webapp_demo` 看上去可以直接当靶场：它有个 `--serve` 模式，`/hello` 返回一份
内存里的 JSON，正是 `benchmark.md` 测的那类动态路由。但它**每个请求都写一行访问日志**，
而那一行要过全局日志锁（一次请求五次）、两次 `vsnprintf`，再 `fwrite` 到 stdout。

实测这个差别很大：同一台机器、同样的负载下，把访问日志关掉，**吞吐从 ~26 000 涨到
~34 500 RPS（+33%）**。拿 demo 当靶场，量到的主要是日志系统的价钱。

所以靶场 `bench/bench_server.cpp` 默认**一个中间件都不装**，把日志变成一根能单独扳动的
旋钮（`--access-log`），于是「日志值多少 RPS」本身也成了一个可以量出来的量。

## 建与跑

靶场默认**不建**，也不进 CI —— 它是量具，不是功能。

靶场建在 webapp 之上，所以**任何已经能建 webapp 的树**，加一个开关重新 configure 就能建它：

```bash
cmake -S . -B build-webapp -DUVCPP_BUILD_BENCH=ON
cmake --build build-webapp --config Release --target uvcpp_bench_server
```

（全新工作区也行，只是要先把 webapp 的依赖拉下来 —— llhttp 与 nlohmann/json 走
`FetchContent`，和建 webapp 是同一套。多配置生成器下 `--config Release` 不能省，
否则建出来是 Debug，读数就没有意义了。）

`UVCPP_BUILD_BENCH=ON` 配一个 `UVCPP_BUILD_WEBAPP=OFF` 的树不会报错，只是不建靶场
（靶场是 webapp 上的一个服务）。

Windows 上 `copy_test_dlls` 会把 `uvcpp.dll` / `uv.dll` / `llhttp.dll` 一并拷到靶场输出
目录 —— 少了这一步，靶场会以 `0xc0000135` 静默退出，而**静默退出的靶场在压测脚本眼里
和"服务起不来"是同一件事**，很容易被误读成服务端的锅。

跑起来：

```bash
uvcpp_bench_server --port 8080
```

启动横幅会把这份读数的**全部配置**打出来 —— 版本、端口、是否装访问日志、日志等级、
内存池开关、try_write 开关。这不是装饰：**一份不带配置的 RPS 不是结论，是传闻**。端口传
`0` 时由内核分配，实际端口只有横幅里有。

| 开关 | 作用 |
|---|---|
| `--port N` | 监听端口，`0`（默认）= 内核分配 |
| `--access-log` | 装上访问日志中间件（用来量它的价钱），默认不装 |
| `--log-level L` | `TRACE`/`DEBUG`/`INFO`/`WARN`/`ERR`/`FATAL`，默认 `WARN` |
| `--static <dir>` | 额外把静态根挂到 `/assets`，默认不挂 |

路由只有两条：`GET /json`（内存里预先拼好的 JSON）与 `GET /text`。

## 驱动器：为什么是多个生成器进程

```bash
npm install autocannon          # 本仓不 vendor 它
node bench/driver.js --url http://127.0.0.1:8080/json --proc uvcpp_bench_server \
     --nproc 4 --duration 15 --connections 25
```

单个 `autocannon` 是单线程 JS，**它自己会先到顶**。本机实测：单进程时生成器吃满一个核、
服务端也吃满一个核，两边同时到顶 —— 这种读数是**没有分辨力**的，既说明不了服务端能跑多少，
也说明不了还能不能更快。所以驱动器铺 N 个生成器进程，把生成器这一侧的算力摊到多个核上。

### 判据是「服务端占了几个核」，不是 RPS

驱动器每次都会报服务端占了多少个核，并且**按它判结论**：

| 服务端占用 | 含义 |
|---|---|
| ≥ 0.9 核 | 服务端到顶 —— 这个 RPS **是服务端的能力** |
| < 0.9 核 | 服务端没到顶 —— 这个数只是**生成器的上限**，不能当服务端性能 |

量不到服务端 CPU 时驱动器退出 `3`（**没判**），而不是当成 0 报绿。退出码沿用本仓的
三值约定：`0` 判过 / `3` 前提不满足。

这一条是整页最要紧的规矩。少了它，"RPS 涨了"和"这次生成器恰好更闲"长得一模一样。

## 本机不是一台安静的压测机

量之前先看清机器。本机（2026-09-21）是 **Intel Core Ultra 5 125H，14 核 / 18 线程，
移动端 P+E 混合，3.6 GHz**，而且是一台**有人用的工作站**：基线负载 ~40%、559 个进程、
远程桌面与浏览器常驻。

这有两个后果。

**一、P 核与 E 核差很多。** 服务端线程落在哪一类核上，读数能差一倍。所以量之前**把服务端
钉在一个核上**，别让它中途迁移：

```powershell
$p = Get-Process uvcpp_bench_server
$p.ProcessorAffinity = 1        # 逻辑 CPU 0，在本机是 P 核
$p.PriorityClass = 'High'
```

不钉核时同一个配置连跑两轮能差 **104%**；钉核后落到 ~9%。**9% 也只是能用，不是很好** ——
所以下面说的"相对测量"要按多轮最小值判，不要按单轮。

**二、绝对值只在同一台机器上可比。** `benchmark.md` 那条 **75 791 RPS** 是在另一台机器
（Windows 10 1903）上量的；本机同口径只有 **~35 000**。这不是回归，是硬件不同 ——
**两台的数不能相减，也不能相除。**

## 已经量出来的三件事

单事件循环、`GET /json`、Release、内存池 ON、try_write ON：

| 靶场 | 访问日志 | 生成器 | RPS | 服务端占核 |
|---|---|---|---|---|
| `webapp_demo /hello` | **ON** | 1 × 10 | ~26 000 | — |
| `webapp_demo /hello` | **ON** | 4 × 25 | 19 827 | 0.94 |
| `bench /json` | off | 1 × 10 | **34 483** | 0.93 |
| `bench /json` | off | 4 × 25 | 26 106 | 0.95 |

1. **服务端在每一种配置下都钉在 ~0.94 核** ⇒ 瓶颈在服务端，不在生成器（4 个生成器时
   每个只占 ~42%）。
2. **访问日志值约 25% 的吞吐**（26 000 → 34 483）。它每请求过多次全局锁加两次
   `vsnprintf`，中间件在 `src/webapp/uvcpp_web_middleware.cpp:92`。
3. **连接越多越慢**：10 连接 34 483 → 100 连接 26 106，**服务端 CPU 基本没变**。
   同样的 CPU 干更少的活 ⇒ 存在一个**每次读事件的固定开销**，且它随连接数放大。
   头号嫌疑是接收缓冲：每次读都按 64 KiB 分配，而分配函数**整块清零** ——
   `uvcpp_alloc_arry` 是 `malloc` 紧跟一次 `memset`，见
   `src/uvcpp/uvcpp_alloc.h:102-105`。一次读事件白写 64 KiB，这笔钱与收到多少字节无关。

第 3 条还没有定论（**上表是四次独立运行，不是同一轮的对照**），要坐实它得先把
「按读事件计价」和「按请求计价」分开量。在那之前，它是**嫌疑**，不是结论。

## 这一页不是什么

- 不是读数记录 —— 读数属于跑它的那套硬件加配置，写在 [`benchmark.md`](benchmark.md)。
- 不是回归门禁 —— 靶场不进 CI，本机的噪声也不支持一个绝对阈值。
- 不是「本库比 X 快」的证据 —— 只测了本库自己，没在同样的机器上跑过对照组。
